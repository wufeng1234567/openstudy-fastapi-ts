# 代码质量提升实施方案

> 目标：把后端从「功能可用」推进到「**有设计文档、有测试保护、可持续重构**」的质量水位，全过程不改动现有对外行为。
>
> 六项工作，按依赖顺序推进（测试在前，重构在后 —— 没有测试保护的重构是赌博）：
>
> | # | 工作项 | 产出 |
> |---|---|---|
> | 1 | 设计方案 | `doc/design/<feature>/` 下三份文档：需求规格 / 技术设计 / 任务拆解 |
> | 2 | 项目测试 | `pytest.ini` + `tests/unit/` 纯逻辑单测 + 覆盖率报告 |
> | 3 | 项目重构 | 提取重复代码、收敛职责，测试保持全绿 |
> | 4 | 功能优化 | 学情诊断报告的 Markdown 导出（补齐 PDF 之外的交付形态） |
> | 5 | 代码优化 | 消除裸 `except`、统一日志、补齐类型标注 |
> | 6 | 代码检查 | 语法编译检查 + 静态分析，输出问题清单并逐类清零 |

---

## 0. 为什么这套流程不会弄坏现有项目

**核心策略：只做「加法」，再做「有测试保护的重构」。**

| 工作项 | 高风险做法 | 本方案做法 |
|---|---|---|
| 设计方案 | 让 AI 重构已有模块来「产出」文档 | 对一个**纯新增函数**做设计，文档放 `doc/design/` |
| 项目测试 | 一上来就改代码、顺手「修 bug」 | 先只测**不依赖数据库的纯函数**，测试文件独立在 `tests/unit/` |
| 项目重构 | 边重构边加功能，出问题说不清是哪一步 | **先有绿测试，再重构**；每步重构后必须仍全绿 |
| 功能优化 | 顺手改已有函数的实现 | 只**新增**函数，已有函数一行不改 |
| 代码优化 | 全仓批量替换 | 按文件逐个改，每改一个跑一次测试 |
| 代码检查 | 开一堆规则然后一次性修几百处 | 先看基线，只修**真问题**（未使用导入、裸 except、可变默认参数） |

**三条工程约束**：

1. 新增代码只出现在**新文件**里，或只往已有文件**追加**函数，不改已有函数体。
2. 单测**不连数据库、不连网络、不调模型**。跑测试不需要 `.env`（已验证：目标模块无 DB 也能 import）。
3. 每个阶段结束立刻 `git commit`。出问题 `git reset --hard` 退回上一个 commit，损失不超过一个阶段。

**这个顺序本身就是方案的价值**：测试在重构之前，所以重构有安全网；代码检查在最后，所以前面写的代码能被统一收口。

- `doc/design/` 里的三份文档必须是**针对真实需求**写的，不是从别处抄来的模板；

## 3. 阶段 1：设计方案（约 40–60 分钟）

### 3.1 这次设计什么需求

**选「学情诊断报告支持 Markdown 导出」**，理由：

| 维度 | 说明 |
|---|---|
| 改动性质 | 纯新增 —— 在 `diagnosis_report_service.py` 里追加函数，不改现有 `export_diagnosis_pdf` |
| 依赖 | 零依赖：输入 dict、输出 str，不连库不调模型，单测易写 |
| 用户价值 | 学生想把诊断结论贴进笔记或群聊，PDF 不好复制 |
| 复用度 | 现有 PDF 的数据结构完全可复用，技术设计有实质内容可写 |

### 3.2 生成需求规格

````text

名字用 diagnosis-markdown-export，在里面放三份文档：
01-需求规格.md / 02-技术设计.md / 03-任务拆解.md

这一轮先生成第一份 01-需求规格.md。

## 需求内容

为 OpenStudy 的学习诊断报告新增 Markdown 导出能力。

现有实现是 openstudy-fastapi/app/services/diagnosis_report_service.py 里的
export_diagnosis_pdf(diagnosis: Dict[str, Any], *, user_name: str = "") -> bytes，
它把学情诊断结果渲染成 PDF。现在需要一个平行的
export_diagnosis_markdown(diagnosis: Dict[str, Any], *, user_name: str = "") -> str，
输出结构化的 Markdown 文本，让用户可以复制到笔记、聊天工具或 Markdown 编辑器中。

## 输入数据结构（这是 export_diagnosis_pdf 实际消费的键，必须严格对齐，不要自己发明字段名）

diagnosis 是一个 dict，包含：
- generatedAt: ISO 时间字符串（PDF 里按 [:19] 截断后把 T 换成空格）
- hasData: bool，False 表示用户还没有任何作答记录
- headline: 一句话结论（字符串）
- suggestions: List[str]，下一步建议
- summary: dict，键为 questionsSeen / totalAttempts / overallAccuracy /
           needsAttention / overdueCount / canArchive
- byLevel: dict，键是分档机器码，值是 {"text": 中文名, "count": 题数}
- items: List[dict]，每项键为 level / levelText / questionText / bankName /
         attempts / correctCount / accuracy / overdueDays /
         recommendedIntervalDays / advice
- bySubject: List[dict]，每项键为 subject / questions / attempts / accuracy
- activity: dict，键为 activeDays / totalPractice / averagePerActiveDay /
            peakDayCount / looksLikeBurst

## 需求要点

1. 输出必须是合法 Markdown，标题层级从 # 开始，不要用 HTML 标签。
2. 必须包含：报告标题（含用户名与生成时间）、总览段落、按分档分组的题目清单、
   每道题的题干片段、分档中文名、建议文案。缺少的小节直接省略，不要输出空标题。
3. 分档必须沿用 study_diagnosis_service.LEVEL_TEXT 的中文映射和
   LEVEL_PRIORITY 的排序（反复失守在最前），不要自己造新的分档名，也不要改顺序。
4. 题干可能包含 LaTeX 公式（如 $\overline{A}$）和 Markdown 表格竖线 |，
   导出时必须转义，不能让 Markdown 渲染错乱。
   ⚠️ 注意：现有的 _esc() 是给 ReportLab 用的（转 & < >），
   与 Markdown 的转义规则（转 \ ` * _ [ ] | # 等）是两套不同规则，不要复用 _esc()。
5. 题干过长要截断，上限复用现有常量 _MAX_STEM_CHARS（90 字符），截断后末尾加省略号。
6. 空诊断（hasData=False 或 items 为空）时也要输出一份有意义的报告，
   包含 headline 与 suggestions，不能抛异常、不能返回空字符串。
7. 不得修改 export_diagnosis_pdf、_clip、_esc、_stem_markup 的任何一行行为。
   只允许新增函数，并在 __all__ 里追加新函数名（保留原有名字）。
8. 新增函数必须能被纯函数式单元测试覆盖：不读环境变量、不连数据库、不调模型。

请把以上内容整理成一份规范的需求规格文档，包含：背景与问题、目标用户、
功能需求（分条）、非功能需求（性能/兼容性/可测试性）、边界情况、
验收标准（可检查的条目）、不做什么（明确排除的范围）。
````

### 8.1 建立检查配置（只开真问题规则）

````text
现在给项目建立静态检查配置，但要克制 —— 只开真问题规则，不开风格规则。

新建 openstudy-fastapi/ruff.toml，内容精确如下：

# 设计原则：只开能抓出「真 bug」的规则，不开纯风格规则。
# 理由：这个项目已有大量手写代码，一次性开全量风格规则会产生几百条噪音，
#      反而让人忽略真正的问题。风格统一留给格式化工具，不混进 lint。

line-length = 120

exclude = [
    ".venv",
    "__pycache__",
    "data",
    "htmlcov",
]

[lint]
# 只启用这几个规则集：
#   E  - pycodestyle 错误（真错误，如语法层面的问题）
#   F  - Pyflakes（未使用导入、未定义名字、重复定义 —— 全是真问题）
#   B  - flake8-bugbear（可变默认参数、裸 except 等真 bug 模式）
#   UP - pyupgrade（过时语法，可选）
select = ["E", "F", "B"]

# 明确忽略的规则及理由：
ignore = [
    "E501",  # 行长度 —— 交给格式化，不要用 lint 报
    "E402",  # 模块级 import 不在顶部 —— 本项目多处刻意延迟导入以避免循环依赖
    "B008",  # 函数默认值是函数调用 —— FastAPI 的 Depends() 就是这个模式

]

[lint.per-file-ignores]

"tests/**" = ["B", "E"]
"test_*.py" = ["B", "E"]
````

## 12. 常见问题（都是会真实遇到的）

| 问题 | 现象 | 怎么办 |
|---|---|---|
| **AI 改动了已有函数** | `git diff` 出现 `-` 行 | 立刻打断，`git checkout --` 回退那个文件 |
| **写测试时顺手改了业务代码** | 它说「顺便修了个 bug」 | 拒绝。测试发现 bug 是好事，但修复要单独一个 commit |
| **测试红了就改断言** | 断言从具体值改成 `assert x` | 禁止。先看实际值，判断是测试错还是代码错 |
| **生成一堆连数据库的测试** | 本地跑不起来（没 PG） | 明确说「只测纯函数」，把 `app.database` 相关全部排除 |
| **`pytest` 还是收根目录文件** | 又报 `test_notice.py` 的错 | `pytest.ini` 的 `testpaths = tests/unit` 必须生效；检查是不是在错目录跑的 |
| **`ruff check` 报几百条** | 输出刷屏 | 正常，改造前没有 lint 配置。先只看 `--statistics`，再只处理 `--select F` |
| **删未使用导入导致启动失败** | 服务起不来 | 副作用导入（注册路由/模型）。删之前先问「有没有模块级副作用」 |
| **重构后测试挂了** | 用例失败 | 立刻 `git checkout --` 回退。**不要**调测试让它通过 |
| **pip 装依赖慢到超时** | `pip install` 一直不返回 | 加国内源：`pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple` |
| **一次生成 8 个测试文件** | 大部分是空壳、断言糊弄 | 强制「一次一个文件，绿了再下一个」 |

## 13. 这套流程对外的说法

做完之后，可以这样描述这次工作（都是事实，没有夸大）：

- **设计**：「新功能先写需求规格和技术设计，再拆任务清单，最后才动手实现 —— 文档都在 `doc/design/` 下。」
- **测试**：「核心纯逻辑模块有单元测试覆盖，跑 `pytest` 全绿，任意机器可复现。」
- **重构**：「重构是在测试保护下做的，每步改完都验证测试仍全绿。」
- **检查**：「静态检查只开真问题规则（Pyflakes 全量 + bugbear），`make all` 一条命令跑完检查、测试。」

**避免的说法**：「这个项目代码质量很高」——没有具体依据的自我评价反而扣分。
改成「8 个模块有单测、覆盖率 X%、`ruff --select F` 零告警」，用数字说话。
