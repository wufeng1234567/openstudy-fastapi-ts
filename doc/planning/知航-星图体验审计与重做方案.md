## 1. 问题清单

> 每条按「现象 / 根因（文件 + 行号 + 函数或字段）/ 用户影响」三段给出。

### 1.1 视觉

**V1 · 深色星空全屏覆盖浅色主题**
- 现象：`97-route-compact.png` 中整个图谱区是深蓝黑渐变底 + 高对比白色点阵；`98-route-foundation-compact.png` 中右侧 `ResizableDrawer` 是纯白主题页，左侧仍是深色，明暗割裂。
- 根因：模板第 71 行 `:class="{ 'is-route-mode': routeActive }"`；`KnowledgeWikiPanel.vue:2024-2031` 的 `.kw-map.is-route-mode` 用 `linear-gradient(160deg, #0b1424 0%, #101d33 55%, #0b1526 100%)` + `rgba(178,205,255,0.42)` 点阵**覆盖**了 2022-2023 行本来正确的浅色底 `#fbfcfe`。另有约 13 条 `.kw-map.is-route-mode ...` 暗色覆盖规则（2037、2045-2046、2052、2057-2058、2060、2063、2066-2067、2074-2075、2078）把轮廓、边、节点 halo、圆环、标签全部改成暗色。**设计源头是主动决策**：`知识图谱学习闭环-探索方案.md:209`「航线态内单独使用深色星图背景、发光航道与移动光点作为『眼前一亮』的视觉层」、`:508`「视觉增强：航线态使用深色星图背景…」，`:390` 明确把「全站暗色重绘」列为不做、却保留了「航线态深色星图层」这个例外。该例外直接违反 `dsh-tokens.scss:15`「当前只启用浅色」。
- 影响：与左侧导航、顶部工具栏、右侧抽屉、主题页卡片完全不在同一套视觉语言里；用户判定为「杂乱 UI」，且深底上的标签 `fill:#dbe7ff / stroke:#0b1424`（2074）可读性下降。

**V2 · 炫技动效抢夺注意力**
- 现象：三色渐变航道、发光模糊、流动虚线、沿路径移动的白色光点、当前站脉冲环与呼吸点。
- 根因：SVG `#kw-route-gradient`（81-85，`#5b8def → #7b61ff → #2f9e8f`）、`kw-map-learning-path-glow`（2070，`filter: blur(4px)`）、`kw-map-learning-path`（2071，`drop-shadow` + `kw-route-flow` 流光）、`kw-map-route-comet`（96-98、2072，`animateMotion` + 双重 `drop-shadow`）、`kw-node-pulse` / `kw-route-beacon`（2068-2069、2079-2089）、`KnowledgeRouteCard.vue:93` `kr-card__pulse` 与 `:118` `@keyframes kr-pulse`。
- 影响：视觉焦点是光效而不是"下一步学什么"；与 0.8.0「简洁、靠留白分块」相悖；在浅色体系里这些效果无处安放。

**V3 · 航线卡片是一块孤立的深色玻璃**
- 现象：`93/94` 左下卡片为半透明深蓝黑、蓝紫渐变主按钮、8~9px 密集小字。
- 根因：`KnowledgeRouteCard.vue:73-118`，`.kr-card { background: rgba(10,18,34,0.9); border: 1px solid rgba(116,155,240,0.34); backdrop-filter: blur(16px); box-shadow: 0 18px 50px rgba(0,0,0,0.42) }`，`.kr-go` 用 `linear-gradient(135deg,#6ea2ff,#4d7ff0)`。与本组件 `.kw-card`（2010，白底）、`.kw-graph-panel`（2090，白底）、`.kw-detail`（2127，白底）完全相反。
- 影响：卡片像浮在页面上的另一套产品；94 截图中卡片与右侧白色抽屉并排时冲突最明显。

**V4 · 字号层级过碎**
- 现象：308px 宽的卡片里塞进 kicker、headline、站点数、4 个站名、当前站说明、主按钮、脚注。
- 根因：`KnowledgeRouteCard.vue` 使用 8 / 9 / 9.5 / 10 / 11 / 11.5 / 12px 共七档字号（92-117），并加 `letter-spacing:.08em`；`dsh-tokens.scss:176-178` 只定义 14 / 13 / 12px 三档。
- 影响：中文在 8-9px 下几乎不可读，信息密度过高，是「杂乱」的第二个来源。

### 1.2 信息架构

**IA1 · 页面没有一句话说明「这个页面是干什么的」**
- 现象：图谱视图只有工具栏「主题页 | 知识图谱 | 更新知识百科」和 `kw-graph-hint` 的操作提示；没有任何文字解释知识图谱的用途。卡片标题「知航 · 今日航线」与文案「按图谱连接与学习态为你排好了今天的学习航线」是**系统已经排完之后**才出现的结果，不是用途说明。
- 根因：`KnowledgeWikiPanel.vue:1-178` 模板中无定位层；`知识图谱学习闭环-探索方案.md:130-131` 的一句话定位只写在方案文档里，没有进入 UI。
- 影响：用户看到一张点阵图 + 一堆圆点，无法回答「我为什么要用它」——反馈 2 的直接来源。

**IA2 · 航线一旦激活，所有能看懂图的线索同时消失**
- 现象：93 截图右侧没有图例面板、左下没有操作提示、非航线节点几乎全灰。
- 根因（多处叠加）：
  - `<aside v-if="!routeActive" class="kw-graph-panel">`（118 行）——隐藏类型图例（6 色 + 计数）、隐藏 4 个开关、隐藏学习雷达、隐藏「下一站」按钮 `kw-learn-next`、隐藏四色 `kw-learn-legend`；
  - `kw-graph-hint` 的条件 `v-if="!learningPathItems.length && !routeActive"`（177 行）——隐藏操作提示；
  - `mapNodes` 中 `routeActive.value || ...`（617-618 行）——航线态**忽略类型筛选与「隐藏无关联页面」**；
  - `isMapNodeDimmed()`：`if (routeActive.value && !isRouteNode(node)) return true`（892 行）、`isMapEdgeDimmed()`（901-907 行）——非航线节点与边全部灰化；
  - `applyLearningRoute()`（821-830）强制 `mapLearnMode.value = true`，覆盖用户 localStorage 偏好（`WIKI_LEARN_KEY`，455/463-469）。
- 影响：用户刚进入就被抽掉图例、筛选、说明、操作提示，只剩一张看不懂的深色图和一张卡片——反馈 2、3 的核心根因。

**IA3 · 没有使用说明 / 首次引导 / 空状态解释**
- 现象：无 onboarding、无 `?` 入口、无「这份资料没有前置关系」之类的解释。
- 根因：组件内只有 `WIKI_VIEW_KEY` / `WIKI_LEARN_KEY` 两个 localStorage 键（454-455），没有引导状态；后端返回的 `degraded` / `mode` / `directionAssumed` 前端完全没消费（见 A3）。
- 影响：反馈 7。

### 1.3 交互状态机

**S1 · 进入图谱即自动规划出一条固定航线**
- 现象：93 截图一进来就是 `WSL → D盘 → C盘 → DISM` 四站 + 卡片，用户没有选择权。
- 根因：`switchMap()`（1443-1472）在 `Promise.all([getWikiGraph(...), getLearningRoute(Number(props.activeKbId), 4)])` 中**无条件**请求航线（1454-1457）；`applyLearningRoute()`（821-830）只要 `data.hasRoute && data.stops.length` 就赋值 `learningRoute.value` 并强制开学习态；`routeActive = computed(() => !!learningRoute.value?.stops?.length)`（564）随之为真，触发 V1/IA2 全部副作用。设计源头是 `知识图谱学习闭环-探索方案.md:168`「进入即自动加载航线，无需点击」与 `:139`「按钮更少」——**把"少按钮"误做成了"替用户决定"**。
- 影响：反馈 5；用户既不知道航线从哪来，也无法拒绝。

**S2 · 没有任何切换 / 重算 / 结束入口**
- 现象：`KnowledgeRouteCard.vue` 只 emit `select`（点站点）与 `start`（继续学习）两个事件（55-58）；卡片没有策略切换、没有「换一条」、没有「结束航线」。
- 根因：`refreshLearningRoute()`（832-847）只在 `switchMap()` 里被调用一次；`updateMapNodeLearning()`（1491-1541）只**就地**改被打开那一站的 `task / reason / status`，从不重新请求。方案 `:357`「回流：`watch` 里在从练习路由返回 / `reload()` 后重新 `switchMap()`」、`:157` 第 8 步「重新 `GET /rag/wiki/route`」**未落地**。
- 影响：反馈 4；读完/练完航线不会"活"起来，卡片停在旧站。

**S3 · 「已有航线时点击其他节点」完全未定义**（反馈 6 直接对应）
- 现象：点任意节点都直接打开抽屉，航线卡片不变、不提示、不重算；用户不知道自己点的节点和航线是什么关系。
- 根因：`onMapNodeClick()`（960-967）→ `selectMapNode()`（939-958）→ `openPage()`（1543）这条链上**没有任何 `routeActive` / `isRouteNode()` 分支**；`onRouteStopSelect()`（986-989）也只做 `selectMapNode()`。全组件没有"当前航线上下文 + 用户临时探索"这两个概念的区分。
- 影响：要么用户以为"点别的节点会换航线"（结果没换，困惑），要么以为"点错会弄丢航线"（不敢点）；两种都阻塞探索。

**S4 · 状态只有一个布尔，无法表达过程**
- 现象：`routeActive` 一个 `computed` 同时承担 6 种语义：有数据、切深色皮肤、隐藏右侧面板、忽略筛选、灰化节点、显示卡片（564、71、118、177、617-618、891-907、169）。
- 根因：没有 `planning / offRoute / recomputing / degraded` 等状态；`routeLoading`（492）只用于卡片 `is-loading` 透明遮罩。
- 影响：无法做出「正在规划」「你已偏离航线」「换策略重算中」这类必要反馈——反馈 3。

### 1.4 航线算法

**A1 · 起点、站数、策略全部写死**
- 根因：
  - `plan_learning_route(pages, links, learning_by_page, *, max_stops=5, focus_page_id=None, page_signals=None)`（`learning_route_service.py:297-305`）没有 `strategy` / `start_page_id` / `target_page_id`；
  - `_priority()`（173-206）是唯一评分函数（诊断病灶 > 未读 > 低正确率 > 连接度）；
  - 无 focus 时 `seed = max(component, key=rank)`（354-359），基于最大连通分量 + 确定性打分，**每次结果相同**；
  - `getLearningRoute(kbId, maxStops = 4)`（`workspace.ts:256`）与 `switchMap():1456` 硬编码 4 站；
  - `GET /rag/wiki/route`（`rag.py:1055-1062`）只有 `kbId / maxStops / focusPageId` 三个查询参数。
- 影响：反馈 4、5；用户无法表达「我想打基础」「我想从这页开始」「我要学到这页为止」。

**A2 · 三种策略其实已经在代码里，只是被压成了一条评分**
- 根因：`learning_route_service.py` 已定义 `ROLE_FOUNDATION / ROLE_REPAIR / ROLE_EXPLORE / ROLE_PRACTICE / ROLE_WEAK / ROLE_REVIEW`（38-43）与 `ROLE_LABELS`（45-52）；`_collect_prerequisite_ancestors()`（209-256）就是「打基础」；`_priority()` 的 `weakCount` 权重（184-188）就是「补弱」；`all_mastered` 分支（393-395）+ `ROLE_REVIEW`（436-437）就是「复习」；`while` 循环沿 `adjacency` frontier 扩展（376-391）就是「拓展」。这些能力**已存在但未参数化暴露**。
- 影响：重做成本很低，不需要新算法、不需要 LLM、不需要新表。

**A3 · 降级信息前端完全没消费**
- 根因：`build_learning_route()` 返回 `degraded`（741-746：`noPracticeData / noQuestionSource / noPrerequisiteEdges / allMastered`）、`mode`（750）、`directionAssumed`（751）、`headline`、`summary`、`stats`；而 `applyLearningRoute()`（821-830）**只读 `hasRoute` 与 `stops`**。方案 `:210-216` 承诺的四档空状态全部未落地。
- 影响：用户看不到「这份资料没有前置关系」「还没有练习记录」「全部已掌握」的解释，航线被当成"系统很懂我"，实际可能是 fallback——反馈 2、3。

**A4 · 视觉上伪造了不存在的「先学顺序」**（违反 0.8.0「不伪造」）
- 根因：`learningPathD`（814-819）把 `learningPathItems` 的所有站**无条件**用 `M/L` 连成一条蓝色发光折线；而 `build_learning_route()`（720-732）返回的 `edges` 只包含 `link_type == 'prerequisite'` 且两端都在航线上的真实边，**前端根本没有使用 `route.edges`**（`applyLearningRoute()` 只取 `stops`）。另一方面 `plan_learning_route()` 的补站循环从**无向** `adjacency` 的 frontier 取候选（376-391），相邻两站之间可能只有 `related/mention` 边，甚至没有直接边。于是界面画出了一条"看起来有先学顺序"的航道，其中若干段没有真实依据。
- 影响：把启发式排序包装成「按图谱前置关系为你排好了」，属于数据可信度问题；也直接连到 D2。

**A5 · 前置方向约定未告知用户**
- 根因：`directionAssumed`（751）与方案 `:239` 约定「`from_page_id` 是 `to_page_id` 的前置」，但前端无处展示；`linkTypeLabel('prerequisite') === '先学'`（1272）只在抽屉的链接列表里出现，航线态看不到。
- 影响：用户无法判断箭头方向的含义，遇到顺序反直觉时无从理解。

### 1.5 演示材料

**D1 · 资料夹主题混杂，不是学习材料**
- 现象：93/94 截图航线为 `WSL → D盘 → C盘 → DISM`；图谱里还有 `智能体 / LLM 智能体 / 工具调用 / 反射式智能体 / Docker Desktop / Ubuntu / TEMP / 方案A:快速回血 / C盘迁移方案 / Gradle / VS` 等，来自「C 盘迁移」「智能体」等互不相关的资料；顶部面包屑是「默认资料夹1」。方案 `:509` 实施记录写的是「读 WSL 主题页」。
- 根因：演示直接复用了默认资料夹，没有为星图准备专门材料。这些是运维/工具笔记，知识点之间没有"先修关系"。
- 影响：航线看起来像随机跳转，无法演示「先学 A 再学 B」——反馈 8。

**D2 · 当前演示其实跑在 `fallback` 模式，没有一条前置边**（关键实证）
- 现象：93 卡片 headline 是「按图谱连接与学习态为你排好了今天的学习航线」。
- 根因：这句文案精确等于 `_headline_for()`（`learning_route_service.py:628-639`）中 `prerequisite_edge_count == 0` 时的最后一个 `return`；同时 `plan_learning_route():507` 会把 `mode` 置为 `'fallback'`、`degraded.noPrerequisiteEdges = true`。也就是说：**当前演示资料夹没有 `prerequisite` 边，航线是无向邻接 + 学习态启发式排出来的**，只是前端没有把 `mode` / `degraded` 显示出来（A3），用户误以为系统懂前置关系。
- 影响：反馈 8 的算法侧根因；也是"航线莫名其妙"的真正来源，换主题样式也救不了。

**D3 · 没有可演示的学情，三种策略无差异**
- 根因：混杂资料夹没有对应的 `UserPracticeLog` / `QuestionSource` 锚点，`degraded.noPracticeData` 与 `noQuestionSource` 为真；`_load_diagnosis_page_signals()`（522-601）拿不到病灶。即使实现三种策略，演示出来也是同一条线。
- 影响：无法体现「补弱」的价值，闭环演示不完整。

## 2. 重做原则

1. **浅色唯一**：全程使用 `dsh-tokens.scss` 的 `--os-*` 与 wiki 组件既有浅色基线（§0.2），对齐 `doc/screenshots/81-wiki-graph.png`。**删除深色星图层这个例外**，不保留 `[data-theme='dark']` 之外的任何暗色分支。
2. **星图只承担一件事**：帮用户决定「下一步学什么」。不承担炫技、不承担进度游戏化、不承担全库状态大屏。任何视觉元素若不能回答「我下一站是哪、为什么、点哪里去做」，就不该出现。
3. **默认不给答案，用户发起才给**：默认是可自由浏览的知识地图；航线是用户主动请求的建议，随时可换、可结束。系统不替用户决定，也不静默覆盖用户行为。
4. **简洁、少按钮**：不新增工具栏按钮、不新增页签/路由/一级菜单；唯一主操作收敛在卡片内，其余用文字链与内联分段控件。工具栏保持现状（`主题页 | 知识图谱` + `生成/更新知识百科`）。
5. **尽量复用**：节点抽屉、搜索建议、类型筛选、学习态圆环、学习雷达、四色图例、`fitMapView()` / `animateMapViewTo()` / `selectMapNode()` 全部原样复用（§0.3）；不为航线新建一套交互语言。
6. **不伪造**：航线只画真实存在的边；`reason` 只引用真实 `RagWikiPageLink`、`QuestionSource.quote`、页面 `sources[].chunkId`、`diagnose().items[].levelText`；不改写已落库关系、不猜前置方向、不 seed 学情。
7. **只读、不落库**：航线每次请求实时计算，不建表、不写 `rag_wiki_page_learning`、不存掌握度、不调 LLM。前端只把「UI 偏好」写 localStorage，绝不持久化航线本身。

### 3.2 如何发起航线、如何选择起点 / 目标 / 策略

**唯一入口：复用右侧面板的 `kw-learn-next`（`KnowledgeWikiPanel.vue:153-156`）**，不新增按钮。

- `idle` 时该位置显示一个浅色主操作：「**规划一条学习航线**」（沿用 `.kw-learn-next` 样式，白底 / `#2f5fce` 文字 / `#e0e8f8` 边框）。
- 点击后进入 `planning`：**在 `kw-graph-panel` 内部内联展开**一小块配置区（不弹 modal、不新开抽屉、不占画布）：

```
┌─ kw-graph-panel（右侧，160px → 规划态临时扩到 220px）──┐
│ 摘要 0 · 实体 9 · 概念 16 …（图例常驻）                │
│ ─────────────────────────────────────────── │
│ 规划学习航线                              [×]  │
│ 我想…  [ 补弱 | 打基础 | 拓展/复习 ]   ← kw-switch 分段 │
│ 从哪开始  [ 自动 ▾ ]      ← el-select，数据源 allMapNodes │
│ 学到哪里  [ 不指定 ▾ ]    ← el-select，可空              │
│ 站点数    [ 4 | 5 ]       ← 小分段，默认 5              │
│ [ 开始规划 ]   ← 唯一主按钮（浅蓝底 / 蓝字）             │

└──────────────────────────────────────────────────┘
```

- **策略**（必选，默认高亮「打基础」但**必须点「开始规划」才执行**）：
  | 策略 | 参数值 | 含义 | 后端复用 |
  | --- | --- | --- | --- |
  | 补弱 | `strategy=weakness` | 优先诊断病灶页 + 低正确率页，并补上它们未掌握的前置 | `_priority()` 原样、`_load_diagnosis_page_signals()` |
  | 打基础 | `strategy=foundation` | 从入度为 0 的未读页起，沿 `prerequisite` 拓扑序推进，跳过已掌握 | `_collect_prerequisite_ancestors()`、`incoming_prerequisite` |
  | 拓展/复习 | `strategy=explore` | 未读优先按连接度扩展；全部掌握时退化为复习链 | `while` frontier 扩展（376-391）+ `all_mastered` 分支（393-395） |

- **目标**：默认「不指定」；指定后航线以该页收尾、其未掌握前置必须排在它之前；目标不可达时返回明确 `reason`，不跨连通分量造边（§5）。
- **站点数**：默认 5（`maxStops` 3~8），不再硬编码 4。
- 取消 / 点面板外空白 → 回到 `idle`，图谱完全不变。

### 3.3 状态机（含「已有航线时点击其他节点」）

前端新增状态字段（组件内 `ref`，**不落库**）：

```ts
type RouteState = 'idle' | 'planning' | 'active' | 'offRoute'
const routeState = ref<RouteState>('idle')
const routeQuery = reactive<{
  strategy: 'weakness' | 'foundation' | 'explore'
  startPageId: number | null
  targetPageId: number | null
  maxStops: number
}>({ strategy: 'foundation', startPageId: null, targetPageId: null, maxStops: 5 })
const offRoutePageId = ref<number | null>(null)
// routeActive 退化为纯数据判据，不再驱动视觉：
const routeActive = computed(() =>
  (routeState.value === 'active' || routeState.value === 'offRoute') && !!learningRoute.value?.stops?.length
)
```

| 状态 | 进入条件 | 图谱表现 | 卡片表现 | 右侧面板 |
| --- | --- | --- | --- | --- |
| `idle` | 默认；或点「结束航线」；或 `active` 时点× | 浅色全量节点，无灰化，无航道；图例/提示常驻 | 不渲染 | 显示「规划一条学习航线」 |
| `planning` | 点「规划一条学习航线」 | 同 `idle`（图谱不变、不预先灰化） | 不渲染 | 内联展开配置区 |
| `active` | 点「开始规划」且 `hasRoute:true` | 浅色底；**仅航线站点**加 2px `#2f5fce` 实线连接 + 站序数字；非航线节点保持正常颜色（最多降到 0.55 透明度，不做 `.is-dimmed` 的 0.12 极暗）；`kw-graph-panel` 与 `kw-graph-hint` **仍常驻** | 浅色卡片显示策略名、headline、站点轨道、当前站、单一主按钮 | 图例常驻 + 增加一行航线图例 + 「航线设置 / 结束航线」文字链 |
| `offRoute` | **`active` 时点击了不在航线上的节点**（或搜索选中了非航线节点） | 已打开节点的抽屉；航道降为 `#c7d0e0` 灰实线（表示"暂停"而非失效），站点数字保留 | 卡片顶部出现一行浅色提示条：「你正在看《X》，它不在当前航线上」+ 两个文字链 `[把它设为起点重算]` `[返回航线]`；卡片其余内容不变、不消失 | 不变 |
| 重算中 | 任一 `@recompute` | 卡片显示 `routeLoading` 的浅色 loading（不用 0.7 透明度深遮罩） | 「正在重新规划…」 | 不变 |

**「已有航线时点其他节点」的明确规定（反馈 6）**：

1. `onMapNodeClick()` 在 `selectMapNode()` 之前判断：`if (routeState === 'active' && !isRouteNode(node)) { routeState = 'offRoute'; offRoutePageId = node.pageId }`。
2. **用户探索意图优先**：照常 `selectMapNode()` → `openPage()` 打开抽屉（复用现有链路，不拦截、不弹确认框）。
3. **航线绝不静默丢弃**：`learningRoute` 保留、`routeStopsView` 保留、卡片保留；只把航道视觉降级为灰色「暂停」态。
4. **绝不自动重算**：点一个节点不应让整条航线突然变化（避免失控感）。只有用户显式点「把它设为起点重算」才以该 `pageId` 作为 `startPageId` 重算并回到 `active`；点「返回航线」或关闭抽屉则回到 `active`。
5. 点**航线上的**节点：保持 `active`，打开该站抽屉，当前站标记不变（若要"设为当前站"，由卡片站点点击 `onRouteStopSelect()` 承担，语义区分清楚）。
6. 关闭抽屉时若 `routeState === 'offRoute'` 自动回到 `active`（在 `closeDetail()` / `watch(detailVisible)` 中处理），避免 hover 一下就永久停在偏离态。

### 3.4 航线如何切换 / 重算

**控制方式（不新增工具栏按钮）**：

| 入口 | 位置 | 行为 |
| --- | --- | --- |
| 策略分段 | 卡片头部一行 3 个可点文字标签（复用 `kw-switch` 样式，非按钮组） | 点即带新 `strategy` 重算，卡片立即显示新策略名 |
| 「航线设置」文字链 | 右侧 `kw-graph-panel` 底部（`kw-learn-next` 旁） | 重新展开 `planning` 配置区，可改起点/目标/站数 |
| 「把它设为起点重算」 | `offRoute` 提示条内 | 以该页为 `startPageId` 重算 |
| 「结束航线」文字链 + 卡片 `×` | 卡片右上角 / 面板底部 | 回 `idle`，清除航道与灰化，筛选完全恢复 |
| 自动回流 | `openPage()` 的 `recordWikiPageView().then(...)` 之后、以及从练习路由返回 / `reload()` 后 | 用**当前 `routeQuery`** 重新 `GET /rag/wiki/route`，实现方案 `:157` 第 8 步「航线重算、自动前移」；失败时保留旧航线并给轻提示，不空白 |

**三种策略的切换成本**：后端只需把 `_priority()` / `_collect_prerequisite_ancestors()` / `all_mastered` 分支参数化（§5.2），**不新增数据源、不新增表、不调 LLM**；前端只换 `routeQuery.strategy` 再请求一次。切换后 `headline` / `reason` / `roleLabel` 会自然变化，用户能直观看出差别。

**`routeQuery` 只存组件内存**；最多把「上次用的策略」写入 localStorage（新键 `openstudy.workspace.wikiRouteStrategy`，与 `WIKI_VIEW_KEY` 同风格）作为默认值，**航线数据本身不持久化**。

1. `知识图谱学习闭环-探索方案.md:143-144` 的**原定目标场景就是《概率论》课件**，`:190-197` 的 UI 草图、`:311-323` 的 API 示例、`learning_route_service.py:272-277` 的 `_route_reason()` 文案（「《贝叶斯公式》有 3 道题反复失守…而本页是它的前置」）全部以条件概率 / 贝叶斯为例——换主题要重写大量既有文案，选概率论零成本。
2. 概率论第一章的前置关系天然是清晰 DAG，容易被 `knowledge_graph_service.py:148-152` 的抽取提示词命中「前置」关系（`{"source":..,"target":..,"type":"前置","description":"关系的原文依据","strength":8}`），再由 `_link_type_for_relation()`（`wiki_service.py:523-525`）映射成 `prerequisite`。
3. 93 截图左侧对话已有「这题：A、B 为随机事件，P(A)=0.4…」，说明库里已有概率论题目，接同源题/诊断更顺。
4. 数学主题页可复用 `LatexRenderer`（`KnowledgeWikiPanel.vue:391`）渲染公式，抽屉无需改造。

### 6.4 文档切分与主题页设计

**主材料：`概率论-第一章-讲义.md`**（一份 Markdown，UTF-8，约 2500–3500 字）

- 结构：`# 概率论 第一章` → 6 个 `##` 小节，每节 300–500 字，与该知识点一一对应。
- 每节固定四段（对应 `RagWikiPage.sections[]`）：`定义与记号` / `公式与推导` / `一个例子` / `常见误区`；公式用 LaTeX（`$...$` / `$$...$$`），由 `LatexRenderer` 渲染。
- **每节末尾必须有一句显式的先修句**，这是抽出「前置」关系的关键原文依据，例如：
  - ② 节末：「学习本节前需先掌握《随机事件与样本空间》中的事件运算与样本空间概念。」
  - ③ 节末：「条件概率建立在《概率的公理化定义与性质》之上，需先理解概率的加法公式。」
  - ④ 节末：「全概率公式是《条件概率与乘法公式》的直接应用，必须先掌握乘法公式。」
  - ⑤ 节末：「贝叶斯公式需要《条件概率与乘法公式》与《全概率公式》两处前置知识。」
  - ⑥ 节末：「随机变量的定义依赖《概率的公理化定义与性质》中的概率空间。」
  - 正文里同时自然提及其它主题名（不加 `[[page:..]]`，因为 seed 时还没有 pageId），让 `linkify_wiki_pages()` / `refresh_wiki_page_links()` 之后能补出 `mention` 内链，图谱更饱满。
- 分块：走 `document_pipeline.process_document()`（`rag.py:411`），每节尽量落在 1–2 个 chunk，保证 `source_chunk_ids` 精确、`QuestionSource` 能锚回具体小节。

**配套：`概率论-第一章-习题.md`**（或复用现有题库 + `QuestionSource`）

- 每节 2–3 道题，其中 ⑤ 贝叶斯公式配 3–5 道；题目带 `QuestionSource(doc_id, chunk_id, quote)` 锚点（现有 `app/models/question.py`）。
- 演示前**真实作答并故意做错几道**，让 `UserPracticeLog(is_correct, create_time)` 产生 `repeated_failure / lapsing`，`diagnose()` 才有病灶，`_load_diagnosis_page_signals()` 才能反查到 ⑤。**不要 seed 答题流水**。

**主题页设计（6 张 `RagWikiPage`）**

| 字段 | 取值 |
| --- | --- |
| `title` / `normalized_title` | 上表标题；`normalized_title` 由 `_normalize_title()` 生成 |
| `page_type` | 统一 `concept`（图例只用一种橙色 `#F08A24`，视觉更干净；也便于和现有 6 色图例对照） |
| `aliases` | 中英别名，如 `["条件概率", "Conditional Probability"]`，供 `refresh_wiki_page_links()` 识别 |
| `summary` | 一句话，含该节核心公式（LaTeX） |
| `sections` | 4 段：`[{heading, body, sourceChunkIds:[...]}]`，`sourceChunkIds` 必须是真实 chunk id |
| `source_refs` / `source_doc_ids` / `source_chunk_ids` | **必须来自真实上传资料**（`wiki_service._source_refs()`, `wiki.py:65-68`），不可留空 |
| `status` | `ready`（`WIKI_READY`），`generated_by` 由 `build_wiki_pages()` 写入 |
| `entity_ids` | 由 `build_wiki_pages()` 关联实体填充，`_rebuild_links()` 据此把实体关系落到页面边 |

### 6.5 导入方式（优先走现有链路，不直接改库）

**主路（推荐，最诚实、可复现）**：

1. 新建**独立资料夹**「概率论 · 第一章」（`POST /rag/knowledgeBase`，`KnowledgeBaseCreate`），**不污染现有「默认资料夹1」、不改用户数据**。
2. `POST /rag/document/upload?kbId=<新>` 上传讲义 + 习题（`rag.py:363-435`；走 `parse_file → analyze_material → create_document → document_pipeline.process_document`，自动分块、向量化、生成 `RagDocumentChunk`）。
3. `POST /rag/knowledge-graph/build`（`KnowledgeGraphBuildRequest{kbId, force:true}`，`rag.py:938-959`）→ `knowledge_graph_service.build_graph()` 抽实体与「前置」关系 → `rag_graph_relation`。
4. `POST /rag/wiki/build`（`WikiBuildRequest{kbId, force:true, limit:30}`，`rag.py:1080-1113`）→ `build_wiki_pages()`（`wiki_service.py:791`）生成 6 张主题页 → `_rebuild_links()`（533-636）把 `relation_type == "前置"` 经 `_link_type_for_relation()`（523-525）写成 `RagWikiPageLink(link_type='prerequisite', source='graph', weight=rel.strength)`。
5. 校验（**必须做，否则会重演 D2**）：
   - `GET /rag/wiki/graph?kbId=` → `edges` 中 `type === 'prerequisite'` 应 ≥ 5 条；
   - `GET /rag/wiki/route?kbId=&strategy=foundation` → `mode === 'graph'`、`stats.prerequisiteEdgeCount >= 5`、`degraded.noPrerequisiteEdges === false`、`stops.length === 5`；
   - 若前置边不足：**先修正讲义里「学习本节前需先掌握 X」的表述并以 `force:true` 重跑第 3–4 步**，不要手工编边。
6. 学情：真实打开几张主题页（`POST /rag/wiki/pages/{id}/view` 自动记录）、真实做错几道贝叶斯题，再演示「补弱」。

**为什么不能只用手动建页 API**：`create_manual_wiki_page()`（`wiki_service.py:1646-1699`）会把 `source_refs / source_doc_ids / source_chunk_ids / entity_ids` 全部置空、`generated_by="manual"`、`page_type="topic"`；`add_wiki_page_link()`（1822-1876）只写正文 `[[page:id|锚文本]]` 内链，由 `get_wiki_graph()`（2279-2296）即时补成 `mention` 边，**不产生 `prerequisite` 边**。纯手动建页会得到「无真实来源 + 无前置边 + `mode:'fallback'`」的空壳，既违反 0.8.0「没有真实来源不伪造」，也无法演示航线。

**Seed 兜底（仅演示环境，须显式标注 `demo`）**：若模型抽取在演示机上不稳定，可用脚本按 `app/models/wiki.py` 直接写三张表，但必须遵守：

```
rag_wiki_page       : user_id, kb_id, title, normalized_title, page_type='concept',
                      aliases[], summary, content_md, sections[{heading,body,sourceChunkIds}],
                      source_refs[{docId,chunkId,docName,chunkIndex,quote}],  ← 必须指向真实 chunk
                      source_doc_ids[], source_chunk_ids[], entity_ids[],
                      status='ready', version=1, generated_by='demo'
rag_wiki_page_link  : user_id, kb_id, from_page_id, to_page_id,
                      link_type='prerequisite', weight=1..10, source='demo'   ← 用 'demo' 而非 'graph'，
                      每条边都要能对应讲义里那句「学习本节前需先掌握 X」   ← 便于与真实抽取区分
rag_wiki_chunk      : page_id, section_index, section_title, content, source_chunk_ids[]（可选，供检索）
```

- **绝不 seed** `rag_wiki_page_learning` / `user_practice_log` / `question_source` / `study_diagnosis` 相关表——学情必须由真实点击与作答产生，否则「补弱」演示一用就露馅。
- 唯一约束注意：`rag_wiki_page` 有 `uk_rag_wiki_page_title(user_id, kb_id, normalized_title)`；`rag_wiki_page_link` 有 `uk_rag_wiki_page_link(user_id, kb_id, from_page_id, to_page_id, link_type)`（wiki.py:42-48、134-141），seed 前先清该演示 kb 的旧数据。
- seed 只作为**兜底**，交付演示仍以主路为准，并在演示说明里注明数据来源。
