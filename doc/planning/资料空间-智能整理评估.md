# 智能整理现状评估与语义化改造建议

## 1. 结论

当前「智能整理」不是语义理解，而是**确定性规则清理**：

- `process_deep_plan` 调用 `material_organizer.analyze()`，没有调用 LLM。
- `material_organize_contract.py` 有 LLM 契约和提示词，但没有任何调用点。
- `image_layout` 只看图片前后的文字位置，没有读取图片内容。
- `duplicate_blocks` 只按规范化文本完全相等判断，没有代码/公式保护。

因此当前可以做到“稳定清理”，但不足以支撑“真正理解上下文、整理乱序内容、理解图片”的评委级卖点。

## 2. 现有缺陷

### 2.1 没有语义理解

当前 deep 整理的阶段只是：

```text
structure -> images -> preview
```

阶段之间只是 sleep，没有真正的模型分析。

### 2.2 文本只能删，不能重排

`_deep_changes` 只产生：

- 文件名/学科/资料类型/内容统计
- 图片关联/图片移动/图片剔除
- 重复/噪声/无关短句剔除

没有章节乱序、题目乱序、答案错位、段落顺序调整等结构操作。

### 2.3 代码块会被当作普通段落

`build_blocks` 没有识别 Markdown fenced code：

```text
```python
...
```
```

代码行被标成 `paragraph`。当重复代码行长度超过 60 字符时，`duplicate_blocks` 会把它当成「重复段落」建议剔除。

已实测：重复的长代码行会进入 duplicate 建议。

#### 2.3.1 非 Markdown 格式的代码问题

上面只覆盖了 Markdown fenced code。Word、TXT、PDF 文件没有 `` ``` `` 围栏，当前解析链路会丢失代码信息：

- `_BlockBuilder.add_text()` 只写入 `{"type": "text", "content": ...}`，没有 `code` / `language` / 来源样式。
- `_emit_paragraph()` 只提取文字和图片，忽略 Word 的 `w:pStyle`、`w:rFonts`、段落底纹、缩进等代码线索。
- TXT 只有纯文本，没有结构。
- PDF 用 `pypdf.extract_text()`，字体和版式信息基本丢失。

结果：

- Word 里用 Consolas、代码样式或灰色底纹排版的代码，会被当成普通段落。
- TXT 里的 `def`、`class`、`#include`、`SELECT` 等代码行没有保护。
- PDF 里的代码块更容易被拆成普通段落，甚至被重复检测误判。

因此代码保护不能只在 `build_blocks()` 里补 Markdown 围栏，必须从文件解析层开始补。

### 2.4 图片没有语义理解

`image_layout` 仅依据：

- 图片最近是题目还是标题
- 图片前后文字是否包含「如图/下图」
- 图片是否紧挨日常闲聊

它不知道图片里是公式、电路图、代码截图、题目配图还是装饰图，因此会误判正常图片，也不能真正判断图片和上下文的关系。

### 2.5 误剔除风险

- `duplicate_blocks` 不区分代码、公式、答案、表格。
- `off_topic_blocks` 靠关键词命中，可能误伤含有“天气/咖啡”等词的正常技术举例。
- `garbage_blocks` 只针对习题/试卷的部分编号行，规则脆弱。

## 3. 目标能力

### 3.1 文本整理

- 检测章节标题编号乱序（第一章、第二章、第三章被调换）
- 检测题目编号乱序
- 检测答案/解析与题目分离
- 检测段落重复、页眉页脚、OCR 噪声
- 生成 `reorder_blocks`、`move_block`、`merge_sections` 等结构化操作
- 代码块、公式、答案默认只读，不参与剔除

#### 3.1.1 非 Markdown 代码识别方案

**Word / DOCX**

在 `_emit_paragraph()` 读取段落 XML 线索：

- `w:pStyle`：`Code`、`代码`、`HTML Preformatted`、`No Spacing` 等
- `w:rFonts`：Consolas、Courier New、Source Code Pro、Fira Code 等等宽字体
- `w:pPr/w:shd` 或 `w:pBdr`：代码块常见灰色底纹/边框
- 连续多个短段落、缩进稳定、包含代码符号（`{}`、`;`、`=>`、`#include`、`def`、`class`、`SELECT`）

输出块提示：

```json
{
  "blockId": "B0021",
  "kind": "code",
  "language": "python",
  "confidence": 0.94,
  "evidence": "Word 段落样式=Code，字体=Consolas，连续 7 行缩进一致"
}
```

**PDF**

- 首选 `pdfplumber` 的字符级坐标和字体信息（如果依赖可用）
- 退化为文本模式检测：连续行缩进、代码符号密度、等宽特征、代码关键字
- PDF 没有字体元数据时置信度降级，默认只作为「疑似代码」保护，不生成剔除建议

**TXT / MD**

- 优先识别 fenced code
- 补充 4 空格/制表符缩进代码块
- 识别 shebang、`def/class/function/const/let/var/import/from/#include/package` 等语言无关入口
- 仅在连续块满足阈值时标记为代码，避免把普通缩进列表误判

**存储与使用**

- `RagDocument` 增加内部 `content_structure` JSON 字段（不给用户新增界面）：
  - `blockId`
  - `start` / `end`
  - `kind`: `paragraph` / `code` / `formula` / `table` / `answer`
  - `language`
  - `confidence`
  - `evidence`
- `build_blocks()` 接受 `content_structure`，优先使用解析器产出的块类型，而不是只看正文。
- `duplicate_blocks()`、`garbage_blocks()`、`off_topic_blocks()` 全部跳过 `code` 块。
- 代码块完整重复时只做低置信度提示：
  - `该代码块与前文完全重复，可能是重复粘贴`
  - 默认不勾选
  - 不参与「一键全选剔除」
- 代码块内公式、注释、答案仍然保持只读。

### 3.2 图片整理

- 识别图片类型：公式截图、题目配图、结构示意图、代码截图、装饰图
- 结合图片内容 + 前后文 + 所在章节判断归属
- 仅在高置信度、可解释证据下建议移动或剔除
- 图片剔除必须保留原图，支持回退

### 3.3 预览与确认

- 点击「智能整理」先弹确认，不直接开始
- 预览按「结构调整 / 内容清理 / 图片整理 / 元信息」分组
- 每条显示证据、置信度和影响范围
- 所有 AI 建议默认不勾选
- 不增加独立任务中心或额外页面

## 4. 推荐实现路线

### P0：先修安全问题

1. `file_parser` 在 DOCX / PDF / TXT 解析阶段产出 `code` 块提示，不只依赖 Markdown 围栏
2. `build_blocks` 读取 `content_structure`，增加 `code` / `table` / `formula` / `answer` 类型
3. `duplicate_blocks` 跳过代码、公式、表格、答案
4. 代码块完整重复时才允许作为低置信度建议，默认不勾选
5. 整理预览加确认弹窗

### P1：真正的结构化文本整理

1. 启用已有 `material_organize_contract.build_llm_messages`
2. 让 LLM 只输出结构化 ops：
   - `reorder_blocks`
   - `move_block`
   - `merge_sections`
   - `suggest_exclude`
   - `attach_image`
3. 服务端用块锁和白名单校验，非法 op 整份拒绝
4. `apply_plan` 支持块移动/重排，保留公式、代码和答案

### P2：图片语义理解

1. 调用现有视觉模型，对图片生成 caption/type/关键实体
2. 将图片描述与章节/题目上下文一起送入整理模型
3. 生成 `attach_image` / `move_image` / `suggest_exclude_image`
4. 置信度低于阈值只展示，不进入可应用建议

### P3：评测体系

已建立固定测试集：

```text
智能整理测试集/
├── docs/                   9 份文档
├── assets/images/          11 张图片
└── REPORT.md               逐文档问题与当前能力评估
```

测试集覆盖：

- 正常技术文档
- 含代码重复的文档
- 章节乱序文档
- 题目/答案错位文档
- 公式/表格密集文档
- 正常配图与无关图片混合文档
- TXT 无围栏代码
- PDF/Word 风格代码（后续补充 docx/pdf 版本）

验收指标：

- 误剔除率
- 代码/公式保护率
- 乱序修复准确率
- 图片归属准确率
- 用户确认后的应用成功率

## 7. 具体迭代任务

### 7.1 P0-A：解析层块结构

- `file_parser._BlockBuilder` 支持 `text` / `image` / `code` / `table` / `formula`
- `_emit_paragraph` 读取 Word 样式、字体、底纹、缩进
- `_parse_txt` 识别 fenced code、缩进代码、shebang、SQL 等
- `RagDocument` 增加内部 `content_structure` JSON（无新 UI）
- 产出 `blockId/start/end/kind/language/confidence/evidence`

验收：

- 02/06/09 的代码块全部进入 `code`
- 09 的 `# 答案：B` 不再成为 heading
- 04 的公式块进入 `formula`
- 07 的表格进入 `table`

### 7.2 P0-B：误剔除保护

- `duplicate_blocks` 跳过 `code/formula/table/answer`
- `off_topic_blocks` 不处理代码和 API 示例上下文
- `garbage_blocks` 不处理代码行
- 代码完整重复只作为低置信度提示

验收：

- 02 的重复代码不产生“删除代码”建议
- 08 的天气/咖啡 API 示例不被删除
- 06 的重复日志只提示、不默认应用

### 7.3 P0-C：Markdown 图片抽取

当前 `_parse_txt` 对 `.md` 只产出一个 text block，`images=0`，测试集里的 `../assets/images/...` 不会进入 `imageMap`。

需要：

- 解析 Markdown 图片引用
- 支持绝对路径/相对路径安全解析
- 将图片写入现有 imageMap
- 无法找到图片时保留引用并提示，不伪造图片

验收：

- 01/03/05/07/08/09 的图片进入图片资产
- 图片墙能展示
- 图片整理能基于真实 imageMap 运行

### 7.4 P1-A：章节/题目/答案结构

- 识别 `第N章`、`第N节`、`第N题`
- 识别答案归属
- 生成 `reorder_blocks` 与 `move_block`
- 保留代码/公式/答案的只读边界
- 在预览中展示结构变化

验收：

- 03 题目从 3/1/2/5 变为 1/2/3/5
- 答案跟随题目
- 07 目录和正文章节顺序一致
- 04 表格行按编号排序

### 7.5 P2：图片语义

- 视觉模型输出图片类型、caption、关键实体
- 结合章节/题目上下文判断归属
- 生成图片移动/剔除建议
- 低置信度只展示，不进入可应用建议

验收：

- 05 四张图分别识别为公式图、协作图、代码截图、电路图
- 08 二维码/海报/装饰图有明确类型
- 03 图片移动到对应题目

## 8. 迭代验收门槛

每个阶段都必须同时满足：

1. 不增加用户可见的新入口
2. 不自动应用 AI 建议
3. 代码、公式、答案零误删
4. 每条建议有 evidence/confidence
5. 至少通过 `智能整理测试集/REPORT.md` 中对应文档的检查

## 10. 评委视角

只做“剔除垃圾”很难形成亮点。真正有辨识度的是：

```text
看得懂结构
说得清依据
改得动顺序
分得清代码和正文
理解图片在讲什么
每一步都可确认、可回退
```

这比再增加一个任务中心更有价值。
