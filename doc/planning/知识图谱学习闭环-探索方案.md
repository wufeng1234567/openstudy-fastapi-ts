### 1.2 缺什么（精确的三个断点）

1. **「前置」关系从未参与任何决策。**
   `RELATION_TYPES` 有「前置」、`RagWikiPageLink.link_type` 有 `prerequisite`、前端有蓝色虚线箭头，但 `buildLearningPath()`（`KnowledgeWikiPanel.vue:812`）只做：`learningPriority()` 打分选起点 → `neighborNodesFor()` **不分方向、不看边类型**地沿任意邻接节点走 5 步。它是一条"看起来像路径的高亮折线"，不是"先学 A 再学 B"的学习顺序。

2. **逐题诊断与知识图谱之间没有映射。**
   `study_diagnosis_service.diagnose()` 只读 `UserPracticeLog + QuestionMain + QuestionBank + UserQuestionError`，**完全没有 import `QuestionSource`**；`learning_loop_service` 的 `healthMap` 按 `subject`（科目）聚合，`todayPlan` 按题聚合。于是诊断说「反复失守，多半是缺前置知识」（`_advice()` 原文），却无法回答「缺的是图谱上哪一个主题页、哪一节、哪段原文」。而 `_wiki_learning_map()` 里已经写好了 `chunk_to_pages / doc_to_pages` 的反查算法——只差把诊断 `items` 喂进去。

3. **路径没有「可执行任务」，也没有真正的回流重算。**
   现有星轨每一站只有 `learningReason()` 一句文案（"已读但还没练过"），没有 `read / practice / repair` 任务、没有题库跳转、没有来源回看、没有微课。练习发生在另一个路由页，回到图谱时 `mapGraph.value` 不会自动刷新（`switchMap()` 只在进入视图/`reload()` 时调用），学习态与航线不会因一次练习而"活"起来。

### 1.3 为什么现在还不算「真正有作用」

图谱目前是**一张给人看的图**：能看结构、能点开页面、能染色学习态，但它不改变用户下一步的行为。三条数据链各自成立却首尾不接：

```
资料 → 实体/前置边 → 主题页 → 同源题 → 练习流水 → 逐题诊断 → ??（断在科目聚合）→ 回到图谱（只更新圆环颜色）
```

用户看到的是"我哪页读过、哪页练过"，系统没有回答"**我下一步该学哪个概念、为什么是它、点哪个按钮去做、做完之后整张图怎么变**"。补齐「前置拓扑 + 诊断反查 + 可执行任务 + 实时重算」这一层编排，图谱才从**可视化**变成**驱动学习闭环的引擎**。关键前提是：所需数据（prerequisite 边、学习态、`QuestionSource` 锚点、逐题诊断、同源题库）**全部已经存在**，缺的只是一个只读编排层。

## 2. 候选方向（4 个不同思路）

> 共性前提：全部只用现有 PostgreSQL 表 + 现有 SVG 图谱 + 现有抽屉，不新增图数据库、不新增一级菜单。

### 方向 A · 知航（学习航线 / 知识星图）—— 编排驱动型
- **思路**：把 `prerequisite` 边构成的 DAG 与学习态、逐题诊断合成一条 3~5 站的航线，系统每次只推「今日一站」，每站带一个可执行任务；读完/练完/答完，节点点亮、航线实时重算并自动前移。
- **用户价值**：不用自己看懂一张几百节点的图；「下一步做什么」永远只有一个答案，且能解释原因。
- **视觉亮点**：现有蓝色虚线前置边串成航道 + `.kw-map-learning-path` 流光 + 星环点亮 + 当前站脉冲环；完成时镜头沿航线平移。视觉元素**全部已在样式表里**。
- **模块闭环**：资料空间 → 图谱(前置边) → 主题页(阅读记录) → 题库/练习(同源题) → 诊断(逐题 level 反查页面) → 图谱(学习态+航线重算)。
- **难度 / 风险**：**低**。1 个只读服务 + 1 个 GET 端点 + 1 个前端 API + 1 个组件改造 + 1 个测试文件；无新表、无模型调用。主要风险是「前置」抽取方向的语义歧义（见 §4.3），可用拓扑入度兜底。

### 方向 B · 知识 CT（图谱诊断修复）—— 诊断驱动型
- **思路**：把 `diagnose()` 的 `repeated_failure / lapsing` 题目经 `QuestionSource` 反查到主题页，在图谱上标「病灶」红晕；沿 `prerequisite` 边**反向回溯**找「病根前置节点」，生成一张"修复处方"（回看原文 chunk → 看解析 → 补练），与 `errorBattle` 的歼灭进度对齐。
- **用户价值**：把"我正确率 53%"变成"你这 3 道题卡在《贝叶斯先验》，因为它的前置《条件概率》还没读"。这是目前所有题库产品都做不到的解释。
- **视觉亮点**：病灶热力扩散、回溯箭头、修复前后对比双态图。
- **模块闭环**：诊断 → 题库锚点 → 图谱 → 主题页/来源回看 → 微课 → 错题歼灭战。
- **难度 / 风险**：**中**。同样需要 question→page 反查（与 A 共用），但"病根归因"容易过度推断：诊断只有相关关系，不能断言因果。必须只呈现「同页关联 + 沿前置边的候选」，措辞克制，否则违反"不伪造"。

### 方向 C · 知识宇宙（闯关 / 解锁）—— 游戏化驱动型
- **思路**：把 prerequisite DAG 变成关卡星系，通关条件 = `learning.level === 'mastered'`（`build_learning_snapshot()` 已定义 ≥80 分且练过），未解锁节点灰化；结合 `errorBattle` 做「Boss 关」，连对 4 次才毕业。
- **用户价值**：进度感、成就感，适合长周期备考。
- **视觉亮点**：星系解锁动画、徽章、进度条、Boss 节点。
- **模块闭环**：图谱 → 练习 → 学习态 → 解锁 → 错题歼灭战。
- **难度 / 风险**：**中高**。需要持久化「解锁/徽章/通关」状态（新表或复用 `RagWikiPageLearning` 扩列），会与"掌握度实时算、不落库"的现有设计哲学冲突；且 `mastered` 判据偏严（需练够 5 题且正确率高），新用户极易卡关、空转。**不适合作为首个闭环版本**。

### 方向 D · 图谱流水线（驱动内容生产）—— 生成驱动型
- **思路**：选一个目标节点，沿前置链自动编排「主题页讲义 + 微课 HTML + 同源题 + 按天处方」成一包，交给智能体 20+ 工具执行。
- **用户价值**：一次点击产出一份完整学习包，展示"系统真懂知识结构"。
- **视觉亮点**：装配线 / DAG 流水线动画、产物卡片墙。
- **模块闭环**：图谱 → 智能体 → 微课 / 学习处方 / 讲义 / 题库 → 导出。
- **难度 / 风险**：**高**。多次 LLM 调用、耗时、产物质量不稳定、与 `buildWikiPages` 后台任务争抢模型额度；且偏"一次性演示"，缺少日常回流，闭环弱。

### 方向对比

| 方向 | 是否有真实闭环 | 新增数据量 | 新增依赖 | 一次交付可行性 | 差异化 |
| --- | --- | --- | --- | --- | --- |
| **A 知航** | ✅ 完整 | 0（全只读实时算） | 0 | ✅ 高 | 前置拓扑 × 逐题诊断 × 图谱，三者首次打通 |
| B 知识 CT | ◐ 偏诊断展示 | 0 | 0 | ✅ 中 | 解释力最强，但归因克制后亮点收窄 |
| C 知识宇宙 | ◐ 需新状态 | 需要新表/扩列 | 0 | ✕ 低 | 游戏化常见，且卡关风险高 |
| D 图谱流水线 | ✕ 一次性产出 | 0 | 多次 LLM | ✕ 低 | 演示感强、日常价值弱 |

## 3. 推荐方案：**知航**（图谱学习航线）

### 3.1 产品命名与定位

- **名称**：**知航**（副标：知识星图 · 学习航线）
- **一句话定位**：**知识图谱不再是一张要看懂的图，而是一条会自己往前走的学习航线——系统按「前置关系 + 学情诊断」算出唯一的下一站，读完、练完、诊断完，节点点亮、航线自动重算。**

### 3.2 为什么选它（最适合现在落地）

1. 三要素**已全部就位**：`prerequisite` 边（`RagWikiPageLink`）、学习态（`build_learning_snapshot`）、诊断+题库锚点（`diagnose()` + `QuestionSource`）；缺的只是一个编排层。
2. **零新增数据**：航线每次请求实时算，不建表、不落库、不漂移——与 `build_learning_snapshot()`「不存掌握度」、`learning_loop_service`「确定性、不调模型」的既有哲学完全一致。
3. **零新增视觉基建**：流光航线、星环、脉冲、前置边箭头、抽屉、雷达全部现成，只改数据源与一张卡片。
4. **按钮更少**：把工具栏「学习路径」按钮去掉（改为进入图谱自动规划），主操作收敛成卡片里的一个「继续学习」。
5. 能真正回答用户的三个问题：*图谱有什么用？我该学什么？学完之后系统怎么变？*

### 3.3 目标用户场景

> 大二学生把《概率论》课件与习题传进资料夹，系统抽出 108 个实体 / 112 条关系，生成 30 张主题页。他打开「知识图谱」，看到一张几百节点的力导图，不知道从哪开始。
> **知航**：图谱自动亮起一条蓝色航道，左下角只有一张卡——「今日一站：条件概率。原因：你有 3 道题反复失守，都落在《贝叶斯公式》，而《条件概率》是它的前置且你还没读过。」点「继续学习」→ 右侧抽屉读主题页 → 抽屉里「去练 8 题」→ 练完回到图谱，这一站的星环从灰变蓝、航道流光前移，下一站变成《贝叶斯公式》。

### 3.4 核心用户旅程（完整闭环）

| # | 阶段 | 真实能力 / 接口 | 系统动作 |
| --- | --- | --- | --- |
| 1 | **资料** | `POST /rag/document/upload` → `document_pipeline.process_document` → `RagDocumentChunk` | 上传、解析、分块、向量化 |
| 2 | **图谱** | `POST /rag/knowledge-graph/build` → `build_graph()`；`POST /rag/wiki/build` → `build_wiki_pages()` + `_rebuild_links()` | 抽实体/关系（含「前置」）→ 落成 `rag_graph_relation` → 生成主题页 → 派生 `RagWikiPageLink.prerequisite` 边 |
| 3 | **规划** | `GET /rag/wiki/route?kbId=`（**新增**）→ 内部读 `get_wiki_graph` 同款数据 + `_wiki_learning_map` + `diagnose()` | DAG 拓扑 + 病灶反查 + 评分 → 3~5 站航线，每站带 `reason` 与 `task` |
| 4 | **进入** | `switchMap()` 并行 `getWikiGraph()` + `getLearningRoute()` | 图谱自动高亮航道与当前站；卡片只显示「今日一站」 |
| 5 | **阅读** | 点节点 → `selectMapNode()` → `openPage()` → `GET /rag/wiki/pages/{id}` → `POST /rag/wiki/pages/{id}/view` → `updateMapNodeLearning()` | 抽屉读页；`view_count+1`，学习态 `unread→reading`，星环就地更新 |
| 6 | **练习** | 抽屉 `goPractice()`（`practice.bankId`）→ `/front/questionPractice/{bankId}/practice/sequential`；无题库则 `askPage('practice')` → `emit('ask', prompt)` 让智能体出题（写入 `question_source` 锚点） | 逐题作答写 `UserPracticeLog(is_correct, create_time)` |
| 7 | **诊断** | `diagnose()` 的 `level / advice / accuracy / streak`；`learning_loop_service` 的 `headline` | 通过 `QuestionSource.doc_id/chunk_id` 反查到页面，得到该页「病灶分」与 `repeated_failure` 前置回溯 |
| 8 | **回流** | 回到图谱重新 `GET /rag/wiki/route` + `GET /rag/wiki/graph` | 掌握度变化 → 节点点亮/星环推进 → 航线重算、自动前移到下一站 → 卡片给出新的「今日一站」 |

闭环成立的关键：**第 3、7、8 步是新增的编排层，其余 5 步全是现有代码**。

## 4. 详细设计

### 4.1 信息架构与入口（按钮只减不增）

- **不新增一级菜单、不新增路由、不新增页签**——严格遵守 0.8.0「只保留知识百科一个入口」。

### 4.3 后端数据与算法（新增 1 个只读服务 + 1 个 GET 端点）

**新增端点**：`GET /rag/wiki/route`（挂在 `app/api/v1/rag.py`，**不修改任何现有端点**）

#### 4.3.1 输入数据（全部来自现有表 / 函数）

| 来源 | 取什么 |
| --- | --- |
| `RagWikiPage` (`status in [ready, stale]`, `kb_id`) | 节点：`page_id / title / page_type / source_doc_ids / source_chunk_ids / entity_ids` |
| `RagWikiPageLink` (`link_type='prerequisite'`) | 有向前置边 `from_page_id → to_page_id / weight` |
| `wiki_service._wiki_learning_map()` | 每页学习态 `learning`（`viewCount / practiceCount / accuracy / masteryScore / level`） |

#### 4.3.2 算法（5 步，全部可单测、可解释）

**Step 1 · 构造前置 DAG 与拓扑序**
只取 `link_type == 'prerequisite'` 的边，用 Kahn 算法求拓扑序；检测环并断环（按 `weight` 保留强边）；入度为 0 的页面构成「起点集」。
> ⚠️ **前置方向的诚实处理**：`_rebuild_links()` 把 `RagGraphRelation.source_id → target_id` 写成 `from_page_id → to_page_id`，但抽取提示词 `_prompt()` 里「前置」示例 `{"source":"实体名1","target":"实体名2","type":"前置"}` 未定义语义方向；前端 `linkTypeLabel('prerequisite')` 译作「先学」。MVP 明确约定 **`from_page_id` 是 `to_page_id` 的前置（先学 from，再学 to）**，并作为展示箭头与 `reason` 文案依据；**绝不改写已落库的关系**。为了不让方向歧义阻塞闭环，评分以「入度为 0 优先 + 学习态」为主、方向只做顺序约束与文案，且在响应里下发 `directionAssumed: true` 供 UI 解释。

**Step 2 · 诊断反查（本方案最核心的新算法，也是 A/B 两方向共用的地基）**
复刻 `_wiki_learning_map()` 已有的 `chunk_to_pages / doc_to_pages` 反查思路，但输入换成 `diagnose()` 的 items：

```
for item in diag.items:                       # 只读，不落库
    src = QuestionSource[item.questionId]    # 可能为空：老题没有锚点 → 跳过，不伪造
    target_pages = chunk_to_pages[src.chunk_id] or doc_to_pages[src.doc_id]
    for page in target_pages:
        if item.level in {repeated_failure, lapsing, overdue}:
            page.weakCount += 1
            page.weakReasons.append(item.levelText / advice / accuracy)
```
- 与 `learning_loop_service._is_available()` / `sds.load_question_meta()` 一致：**题目已被物理删除的孤儿流水（「题目内容已不可用」）必须过滤**，不能生成点进去什么都没有的「幽灵站点」。
- 这一步把「按科目聚合」的诊断升级为「**按图谱节点聚合**」，是相对现有 `healthMap` 的真正差异化。

**Step 3 · 站点评分（确定性、无魔法权重、可解释）**

```
score(page) =
    200 * (1 if page.weakCount > 0 else 0)                      # 诊断病灶优先
  +  40 * weakCount                                            # 病灶越多越优先
  +  30 * (1 if page.learning.level == 'unread' else 0)        # 未读优先
  +  20 * (1 if page.learning.accuracy < 60 and practiceCount > 0 else 0)  # 页面级弱项
  +  10 * (1 if 有未掌握的 prerequisite 前置指向它 else 0)      # 前置-blocking 加分
  +   1 * degree                                               # 枢纽兜底
  - 100 * (1 if page.learning.level == 'mastered' else 0)      # 已掌握降权/跳过
```
- **硬约束（与现有启发式最大区别）**：若目标页存在 `level != 'mastered'` 的 prerequisite 前置页，**前置页必须先出现在航线里**，不能直接把目标页推到第一站。这就是「真正用了前置关系」。
- `repeated_failure` 站点额外沿前置边**反向回溯**一层，把候选病根页排进航线并在 `reason` 里写明（措辞为「候选前置」，不断言因果，避免方向 B 的归因风险）。

**Step 4 · 生成 3~5 站并绑定可执行任务**
每站 `status` ∈ `current / next / locked`；`task` 按现有能力择一，全部能直接点：

| 情形 | task.type | 前端动作（现成） |
| --- | --- | --- |
| `viewCount == 0` | `read` | `selectMapNode()` → `openPage()` → `POST /view` |
| `practice.bankId` 存在 | `practice` | `goPractice()` → `/front/questionPractice/{bankId}/practice/sequential` |
| 无同源题库 | `ask-agent` | `askPage('practice')`，prompt = `请基于知识百科主题页《X》（pageId=..,kbId=..）生成 5 道练习题…`（现有格式） |
| 页面有 `sources` 且 `weakCount>0` | `repair` | `locateSource()` 跳原文；增强阶段附 `getMicroCourse(docId)` 微课入口 |
| `level == 'mastered'` | `review` | 快速复习，不生成假任务 |

**Step 5 · 实时重算、不落库**
`GET /rag/wiki/route` 每次请求都基于当前 `rag_wiki_page_learning` + `user_practice_log` + `question_source` 重算，**不新建航线表、不写掌握度字段**。练习完成后前端重拉即可自动更新——与 `build_learning_snapshot()` 的哲学一致。

## 6. 验收标准与测试建议

### 6.1 功能

- 有 `prerequisite` 边时，航线中任何站点若存在 `level != 'mastered'` 的前置页，**前置页必先出现**（硬约束单测）。
- `mode=fallback`（无前置边）时顺序与现有 `learningPriority()` 结果一致，不报错、不空卡片。
- 每站 `task` 都能点：`read` 打开抽屉并写 `view_count`；`practice` 能跳到真实 `bankId`；`ask-agent` 的 prompt 含真实 `pageId/kbId`。
- 读完 / 练完 / 刷新后，`GET /rag/wiki/route` 结果变化：`learning.level` 与 `build_learning_snapshot()` 一致、星环推进、`stops[0]` 前移。
- 工具栏按钮数 ≤ 改造前；`pages` 视图、搜索、抽屉、编辑、历史版本、页面链接功能零回归。

### 6.2 数据正确性（**不伪造**）

- 所有 `reason` 必须能落到真实证据：`RagWikiPageLink` 边、`QuestionSource.quote`、页面 `sources[].chunkId`、`diagnose().items[].levelText`；不得出现模型编造的解释。
- `question → page` 反查**只认真实 `QuestionSource` 行**；无锚点的老题跳过，不按题干猜页面。
- 题目已被物理删除的孤儿流水必须过滤（对齐 `learning_loop_service._is_available()` 与 `sds.load_question_meta()` 的口径），不产生「幽灵站点」。
- `masteryScore / level` 直接复用 `_wiki_learning_map()` 结果，**不得另算一套掌握度**。
- 同源题库沿用 `_wiki_practice_bank()` 的可见性口径（自己的题库 / `is_public` 题库可练）。
- `stale` 页面可参与但降权；`failed` / `draft` 不进航线。

### 6.3 UI

- 四种空状态（无页面 / 无练习 / 无前置边 / 全掌握）均有明确文案与降级表现，不出现空白卡片或 `undefined`。
- 抽屉打开时图谱冻结、拖拽/缩放/标签显隐行为不变；`route` 请求失败不影响图谱渲染。
- 当前站脉冲、掌握度星环、前置边蓝色虚线箭头、流光航线在 100/300 节点下不遮挡工具栏与右侧面板。

### 6.4 性能

- `GET /rag/wiki/route` 单请求内批量取数：复用 `_wiki_learning_map()` 的批量反查（禁止 N+1）；`diagnose(limit=50)` 沿用现有 `MAX_LOG_ROWS=20000` 上限；路线 ≤ 5 站、`edges` 只回前置边。
- 目标：不含诊断冷启动 < 300ms；前端 `switchMap()` 并行拉取，不串行阻塞首屏。
- 前端不因新增数据触发整图 computed 每帧重算（沿用现有 `mapNodeOffsets` / rAF 只写 DOM 的策略）。

### 6.5 空数据降级用例（建议单测清单）

| 用例 | 期望 |
| --- | --- |
| 无主题页 | `hasRoute:false` + 「先生成知识百科」 |
| 有页面、无 `UserPracticeLog` | `mode:'graph'`、基线航线（入度优先 + 未读优先）、无诊断文案 |
| 有页面、无 `QuestionSource` | `diagnosedPageCount:0`，不编造病灶，航线仍成立 |
| 无 `prerequisite` 边 | `mode:'fallback'`，顺序退化为启发式 |
| 全部 `mastered` | 复习链 + 「全部点亮」文案，不生成假任务 |
| 前置边成环 | 断环成功，`hasRoute:true`，不死循环 |
| 孤儿流水（题已删） | 不计入 `weakCount` |

## 7. 风险与边界

| 风险 | 边界 / 对策 |
| --- | --- |
| **伪造数据** | 航线全部只读实时算；`reason` 只引用真实边 / 真实 chunk / 真实题；无同源题库时给「让 AI 生成练习」而不是假题；无锚点的题不猜页面。继承 0.8.0「没有真实来源不伪造」。 |
| **前置方向语义歧义** | `_prompt()` 未定义「前置」方向；MVP 约定 `from→to` 并下发 `directionAssumed`，评分以入度+学习态为主、方向只做顺序与文案；**不改写已落库关系**，也不让歧义阻塞闭环。 |
| **诊断归因过度** | `repeated_failure` 只呈现「同页关联 + 沿前置边的候选病根」，措辞为「候选/建议」，不断言因果（这是未选方向 B 作为主方案的原因）。 |
| **依赖膨胀** | 不引入 Neo4j / 图数据库 / 新前端图表库 / 新表；只用 PostgreSQL JSON 列 + 现有 SVG 力导图。遵守 0.8.0 边界。 |
| **破坏现有入口** | 不新增一级菜单/页签/路由；`pages`/`map` 双视图、`ResizableDrawer`、编辑器、历史版本、页面链接全部保留；新端点只读，不改 `GET /rag/wiki/graph` 等任何现有契约。 |
| **重复造轮子** | 不重写 `build_learning_snapshot()`、`_wiki_learning_map()`、`_wiki_practice_bank()`、`diagnose()`、`buildLearningPath()` 的渲染层；只新增编排层并复用其输出。 |
| **半成品冲突** | 方案建立在工作区未提交的 `RagWikiPageLearning` / 学习态 / 前端学习路径之上；实施时**不得覆盖或回滚**这 6 个文件的改动（`rag.py`、`wiki.py`、`wiki_service.py`、`test_wiki_service.py`、`workspace.ts`、`KnowledgeWikiPanel.vue`）。 |
| **模型额度** | MVP 全程不调 LLM；只有用户主动点「生成练习」才走智能体，与 `POST /rag/wiki/build` 的后台任务不冲突。 |
| **性能** | `diagnose()` 有 `MAX_LOG_ROWS` 与 180 天窗口上限；航线服务必须批量取数，禁止逐页查询。 |
