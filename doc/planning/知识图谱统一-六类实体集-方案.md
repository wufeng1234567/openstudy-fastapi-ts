# 知识图谱统一与六类实体集整合方案

- 状态：已实施（代码完成，待用户审核）
- 日期：2026-11-10
- 涉及仓库：`openstudy-fastapi`、`openstudy-vue3-ts`
- 关联文档：`doc/planning/学习计划与图谱融合-改造方案.md`、`doc/planning/学习计划与图谱融合-实施记录.md`
- 已确认：
  1. A/B 图都在同一个资料夹内，本轮**不做跨资料夹关联**；
  2. 共享概念放在中央「知识主题」实体集，两个文档来源节点都连向它。

## 1. 目标

### 1.1 产品目标

知识百科只保留两个视图：

1. **主题页**：阅读、编辑、查看来源、来源追溯；
2. **知识图谱**：唯一的图谱视图。

不再有独立的「六类图」入口。

知识图谱内部按六类实体集组织：

- 知识主题（`topic`）
- 题库（`bank`）
- 资料（`document`）
- 网页（`web`）
- 笔记（`note`）
- 图片（`image`）

其中：

- **知识主题节点在中央**，是共享概念的归处；
- **来源节点在周围**，负责提供证据和来源追溯；
- 每个来源节点是一个真实实体集（某份文档、某个题库、某篇笔记、某组图片）；
- 来源节点与知识主题节点之间是真实关系边；
- A 图/B 图不是两张图，而是同一张总图里的两个来源实体集。

### 1.2 技术目标

- 统一图谱主路径，避免「六类图一套数据、知识图谱另一套数据」；
- 合并逻辑先于 UI：同名/同义概念归并成同一个知识主题节点；
- 页面内容合并保留全部来源，不覆盖旧来源；
- 跨组边、桥接节点、孤立节点都有明确的数据语义和视觉表达；
- 图谱画布支持无限扩展，节点拖到左右边缘不会形成裁切直线；
- 资料夹支持导入笔记，笔记能够进入知识图谱。

### 1.3 非目标

- 不做跨资料夹、跨知识库自动合并；
- 不做跨用户图谱合并；
- 不引入 Neo4j 等外部图数据库；
- 不把 `type-check` / `ESLint` 重新纳入本轮验收；
- 不修改题库题目数据本身的归属关系。

## 2. 核心模型

### 2.1 一张总图

```text
                    [网页实体集]
                         \
[题库实体集] —— [知识主题中央区] —— [资料实体集]
                         /        \
                  [笔记实体集]   [图片实体集]
```

- **中央区**：`topic` 节点。共享概念只保留一个节点。
- **周围区**：五类来源节点。每个来源节点代表一个真实来源实体集。
- **边**：
  - `topic -> document/web`：来源边；
  - `topic -> bank`：知识点/题源边；
  - `note -> topic/document`：笔记引用边；
  - `document -> image`：配图边；
  - `topic -> topic`：页面链接/前后置/对比等知识关系。

### 2.2 同一概念的处理

以《智能体理论文档》和《智能体实操文档》为例：

```text
文档：智能体理论文档 ──┐
                        ├──> 知识主题：智能体
文档：智能体实操文档 ──┘
```

- 两个文档来源节点都保留；
- 「智能体」只有一个知识主题节点；
- 页面详情中保留两个来源：
  - 理论文档：定义、原理；
  - 实操文档：步骤、案例、注意事项；
- `source_doc_ids`、`source_refs`、`entity_ids` 做并集；
- 不把两份文档合并成一个文档节点。

### 2.3 跨图桥接节点

「A 图内孤立、却与 B 图节点有联系」的节点定义为 **桥接节点（bridge）**：

- 数据上仍然只保留一个 canonical node；
- 归属仍然是它的主要来源实体集；
- 但它有跨实体集的边；
- UI 显示 `跨图 N` 标记，跨组边使用独立线型；
- 不复制到 B 图，也不因为 A 图内部没有边就删除。

只有 **全局度数为 0** 的节点才是「孤立节点」，进入「未关联节点」列表。

## 4. 数据层设计

### 4.1 主路径

**知识图谱主画布统一使用 `study_map_service.build_study_map` 作为图构建器。**

- 它已经支持 `topic / bank / document / web / note / image` 六类节点；
- 已经返回 `groups` 六类实体集；
- 已经返回 `sourceStats` 六类来源统计；
- 已经与规划建议 `KnowledgeAdviceHost` 使用同一套数据源。

`wiki_service.get_wiki_graph()` 保留用于：

- 主题页详情；
- 页面链接兼容；
- 不参与主画布渲染。

| `note` | 笔记 | `note` 节点 |
| `image` | 图片 | `image` 节点 |

### 4.4 合并规则

#### 4.4.1 实体归一

在 `knowledge_graph_service.merge_duplicate_entities()` 基础上扩展：

1. **精确归一**：`normalized_name` 完全相同且 `type` 相同 → 同一实体；
2. **别名归一**：`RagGraphEntity.aliases` 中包含对方名称或别名 → 同一实体；
3. **同义后缀**：继续保留现有 `_canonical_key()` 的「定义/概念/概述」后缀归并；
4. **类型保护**：`type` 不同不自动合并，避免「模型」这类同名不同义；
5. **候选合并**：名称不完全相同、但类型相同且 embedding 相似度高的情况，进入「合并建议」，不直接自动合并。

合并时：

- `doc_ids`、`chunk_ids`、`aliases` 做并集；
- `mention_count` 相加；
- 迁移 `RagGraphRelation.source_id/target_id`；
- 迁移 `RagWikiPage.entity_ids`；
- 记录 `merge_audit` 日志。

#### 4.4.2 主题页合并

修改 `wiki_service.build_wiki_pages()` 的 existing page 更新逻辑：

- 不再直接覆盖 `source_refs`、`source_doc_ids`、`source_chunk_ids`、`sections`；
- 改为 `merge_wiki_page_from_source()`：
  - `source_doc_ids` 并集；
  - `source_refs` 并集；
  - `source_chunk_ids` 并集；
  - `entity_ids` 并集；
  - `sections` 追加，不覆盖；
  - `generation_meta.sources` 记录所有来源；
  - `summary` 仅在为空时填充；已有摘要不覆盖，来源内容进入分节。

每个 section 增加来源字段：

```json
{
  "heading": "实操步骤",
  "body": "……",
  "sourceChunkIds": [1, 2],
  "sourceType": "document",
  "sourceId": 662,
  "sourceName": "智能体实操文档"
}
```

同标题小节处理：

- 不覆盖，生成两个来源块；
- 页面详情中显示「理论文档」「实操文档」标签；
- 如内容冲突，标记 `conflict`，由用户查看，不自动删改。

#### 4.4.3 关系合并

- 同一 `(source_id, target_id, relation_type)` 合并为一条边；
- `doc_ids`、`chunk_ids`、`evidence` 做并集；
- `strength` 取最大值；
- 方向相反的关系不合并，保留两条并标记 `conflict`；
- 页面链接 `RagWikiPageLink` 保留现有 `weight/source`，页面级来源由 `source_refs` 追溯。

#### 4.4.4 页面 ID 稳定性

- 合并时选择 keeper page，保留其 `pageId`；
- 被合并页面设置 `merged_into_page_id`，状态改为 `merged`；
- 学习记录、题目来源锚点、分享链接继续指向原 pageId 时，通过 redirect 解析到 keeper；
- 不物理删除旧页面，保证历史数据不悬空。

### 4.5 数据库变更

采用现有 `database.init_db()` 的幂等补列方式，不引入 Alembic。

#### `rag_wiki_page`

新增：

```sql
ALTER TABLE rag_wiki_page ADD COLUMN canonical_entity_id BIGINT NULL;
ALTER TABLE rag_wiki_page ADD COLUMN merged_into_page_id BIGINT NULL;
```

含义：

- `canonical_entity_id`：主题页对应的 canonical entity；
- `merged_into_page_id`：被合并页面的 redirect 目标。

#### `rag_graph_entity`

暂不新增列，复用已有 `aliases` JSON 和 `normalized_name`。

#### 可选增强（第二批）

如果别名规模变大，再新增：

```text
rag_entity_alias (
  id,
  user_id,
  kb_id,
  entity_id,
  alias,
  normalized_alias,
  source
)
```

本轮先用 `aliases` JSON + 内存映射即可。

### 4.6 笔记数据

- `note_kb_link` 已有 `(user_id, kb_id, note_id)` 唯一约束，不需要新表；
- `study_map_service` 加载笔记时：
  1. 读取 `ContentReference`；
  2. 读取 `note_kb_link_service.linked_note_ids()`；
  3. 两者并集；
- 即使笔记没有生成主题页，也要在图谱中显示一个 `note` 来源节点；
- 笔记关联后由 `_extract_note_knowledge()` 后台抽取实体并生成主题页。

### 4.7 旧数据迁移

新增一次性命令/脚本 `scripts/rebuild_graph_merge.py`（不自动跑）：

1. 扫描当前资料夹的重复实体/页面；
2. 输出 `merge-report.json`：候选合并、冲突、无法判断；
3. 人工确认后执行 `--apply`；
4. 按文档/笔记/题库来源重建主题页；
5. 重建页面链接；
6. 输出变更前后统计。

不在部署时自动合并，避免误伤历史数据。

## 8. 测试用例

### 后端

1. **同一实体跨文档合并**
   - 构造两个文档，均包含「智能体」「工具调用」；
   - 调用 `build_wiki_pages()`；
   - 断言只有一个「智能体」页面；
   - 断言 `source_doc_ids` 包含两个文档；
   - 断言 `sections` 包含两个来源块。

2. **同名不同义不合并**
   - 构造「模型（机器学习）」与「模型（思维模型）」；
   - 类型/定义不同；
   - 断言保留两个实体/页面。

3. **关系合并**
   - 两个文档都产生 `智能体 -> 工具调用`；
   - 断言一条关系，`doc_ids` 两个，`strength` 不重复累加超限。

4. **跨组桥接**
   - A 文档节点无内部关系，但与 B 文档的 topic 有关系；
   - 断言 `bridgeCount` 增加，节点未被删除。

5. **笔记图谱**
   - `note_kb_link` 关联笔记；
   - `build_study_map(sourceTypes=all)`；
   - 断言 `noteCount > 0`、`groups` 包含 `note`。

## 9. 风险与回滚

| 风险 | 处理 |
|---|---|
| 自动合并误伤 | 先只自动合并高置信名称/别名；相似度合并进入人工确认 |
| 旧页面内容已被覆盖，无法恢复 | 用 `rebuild_graph_merge.py --apply` 按来源重建；保留旧数据备份 |
| 大图渲染卡顿 | 超过 120 节点分组加载；超过 300 节点启用聚合/简化模式 |
| 页面 ID 迁移影响学习记录 | 不物理删除旧页，使用 `merged_into_page_id` redirect |
| `study_map` 数据量扩大 | 增加 `limit` 上限并支持 `seedNodeId` 局部加载 |
| LLM 合并成本 | 只对候选集调用模型；按 doc/entity 分桶，避免全量两两比较 |
| 回滚 | 所有合并记录审计日志；按 `merge-report.json` 反向拆分 |
