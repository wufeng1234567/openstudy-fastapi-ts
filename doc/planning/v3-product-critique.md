## 〇、先给结论（后面是证据）

| 问题 | 结论 |
|---|---|
| 原生表格/公式，学生侧 | ⚠️ **弱刚需**——学生是**消费者**不是生产者；对他们"不乱码"就够了，"能编辑"不值钱 |
| 原生表格/公式，教师侧 | ✅ **真刚需**——教师是**生产者**，要改题、要组卷、要分发；"不能编辑"= 不能用 |
| 流式思维导图/看板 | ⚠️ **演示爽点 > 真实需求**——但它在比赛里的价值**高于**表格，理由是评审维度 |
| "之前方向都错了" | ❌ **这句话错了**。底座没白做，错的是**叙事**——见第二节 |

| 加 5 个功能 vs 讲一个故事 | ✅ **讲故事**。而且必须**只讲一条线**——见第四节 |
| 只做一件事做哪件 | ✅ **原生表格 + 公式贯穿「解析 → 展示 → 导出」全链路**——见第五节 |
| 学生和教师二选一 | ✅ **选教师**。三条教师专属能力见第六节 |

## 一、方向对不对：两条腿，两条不一样的答案

### 1.1 输入处理侧（原生 Word/PDF 表格公式）——分人判断

**先摆一个被忽略的事实**：OpenStudy 的解析侧**已经能提取表格**，但**展示侧和导出侧各做了一半**。

证据链：

```
file_parser.py:667  _emit_table()  —— 解析 Word 表格 → 输出标准 Markdown 表格
                                      （首行当表头 + 插入 | --- | 分隔行 + 单元格 | 转义）
latex.ts:434        renderMarkdownWithLatex()  —— 前端统一管线，先渲公式为占位符 → marked 渲表格 → 回填
                                      DOMPurify ADD_TAGS 含 table/thead/tbody/tr/th/td（latex.ts:501）
bank_export_service.py  —— ❌ 零表格能力
```

我实跑验证了这个缺口（不是靠读代码猜的）：

```python
# 输入：含标准 md 表格 + $E(Z)$ 公式的题面
split_blocks(stem) → [('text','设二维随机变量 $(X,Y)$...'),
                      ('text','| X\\Y | 0 | 1 | 2 |'),      # ← 表格被当成普通文本
                      ('text','| --- | --- | --- | --- |'),
                      ...]
export_bank_docx(...) → docx 文件
Document(...).tables  → 0        # ❌ Word 里一个真表格都没有
```

**结论**：学生**看得到**表格（前端 KaTeX + marked 已渲染），但**导出的 Word/PDF 里表格退化成一堆竖线**。这是产品内部**自相矛盾**——屏幕上像表格，打印出来是乱码。

#### 对学生：**弱刚需**

- 学生是这份文档的**终点消费者**。他要的是"能看清、能打印、能订正"。
- **已经满足**：前端渲染正确（KaTeX 公式 + marked 表格），打印走浏览器打印即可。
- **不值钱的部分**：学生不会去编辑公式。给他 OMML 原生公式和给他一张清晰的图，**对他没有区别**。
- 真正让学生难受的是**别的**：扫不出扫描版 PDF（要 OCR，项目自己的 P0）、错题本 40 道"待消灭"却 0 道"已掌握"。

**判断**：对学生，这是"**及格线**"——做不到是缺陷，做到了不加分。

#### 对教师：**真刚需**

- 教师是**生产者**：导出的卷子他要**改**（改一个数字、换一个选项）、要**凑**（从三个题库各抽几道）、要**发**（发给学生/打印室）。
- **不能编辑 = 不能用**：

| 教师动作 | 现在的产物（退化文本） | 原生结构 |
|---|---|---|
| 改题干里一个数据 | 手动重排整张表的竖线 | 直接改单元格 |
| 从别处复制一行 | 列宽/对齐全乱 | 粘贴即对齐 |
| 调表格宽度 | 不可能（那是文字） | 拖一下 |
| 打印 | 竖线错位、跨页断行 | Word 原生分页 |

**判断**：对教师，这是"**入场券**"——不做，教师端整个不成立。

#### 关键不对称（决定排序）

> **学生只需要"看得清"，教师需要"改得动"。**
> 而"改得动"是"看得清"的**超集**。
> → **做教师侧，学生侧自动受益；反过来不成立。**

### 1.2 输出展示侧（流式思维导图/看板）——演示爽点，但比赛更值钱

**先说它是不是真需求。**

- **思维导图**：真需求，但**不是高频需求**。学生复习时确实想看知识树，但一次备考看一两次就够，不是每天用。而且"边流式输出边渲染"是**技术手段**，不是需求本身——用户从不说"我要边流式边看导图"。
- **动态看板**：**已有能力，只是入口差**。我查到 echarts 已经在两个地方跑着：

```
myQuestion/myStats/index.vue:510,586,608  → 3 张图（趋势 / 科目分布 / 难度分布）
PracticeComponent/ExamSummary.vue:615,676 → 2 张图（成绩 / 题型占比）
```

并且接口真的返回了数据（我实跑 `GET /userStats/overview`）：

```json
{"totalPracticeCount":299,"correctRate":49.5,"totalErrors":40,
 "totalMastered":0,"studyDays":24,"byQuestionType":[...]}
```

**所以"动态数据看板"这个需求，产品里已经实现了 80%。** 用户提的"做看板"，实际是"**已有看板没人看见/不好看**"——这是**包装问题**，不是**能力缺口**。

#### 那它对比赛值不值钱？值。但理由和需求强度无关

回到赛事依据（`doc/competition/讲稿与答辩预案.md:19-27`）：

| 评审维度 | 权重 | 哪条腿更能打 |
|---|---|---|
| 场景价值 | 25% | 两边都能打 |
| 产品完成度 | 25% | **输入侧**（补齐闭环：解析→展示→导出） |
| 技术实现质量 | 20% | **输入侧**（OMML/表格是硬骨头） |
| **创新性** | **15%** | **输出侧**（思维导图/实时可视化，视觉冲击直接） |
| 路演与团队协作 | 15% | **输出侧**（演示效果） |

**判断**：

- **创新性维度（15%）**：输出侧的思维导图/实时图表**视觉冲击直接**，评委一眼记住。输入侧的表格公式，在 PPT 里**很难演示**——"你看，这个表格现在能编辑了"远不如"你看，它一边说一边长出一棵树"有画面感。
- **完成度/技术质量维度（45%）**：输入侧赢。它把"解析→展示→导出"这条链**真正闭环**，且是硬技术。
- **加权后**：**输入侧（45% 相关维度）> 输出侧（30% 相关维度）**。

#### 两者分离时，哪个对比赛更值钱？

> **输入侧更值钱，但输出侧更好演示。**
> 正确的解法不是二选一——**是用输出侧当钩子，用输入侧当内核**。见第四节主线故事。

## 二、「之前的修改方向都错了」对不对

### 2.1 用户点名的四件事，我逐个去看了代码

| 用户说"白做了"的 | 实际代码状态 | 判定 |
|---|---|---|
| 英语模块 | 前端 8 个 Vue / **8,482 行**；后端 `english_practice.py` 28KB + `english_wordbook.py` 26KB + `tts.py` 7KB；19~20 个 `(english)`/`(ocr)` 提交 | ✅ 已成型 |
| 记忆曲线 | `app/services/english/spaced_repetition.py:2` —— **SM-2 简化版，2026-10-26** | ✅ 已实现 |
| 听写三模式 | 提交 `92c0e86`「听写页三种练习模式 + 播放速度/间隔可调」 | ✅ 已实现 |
| 学习统计合并 | 提交 `4f82888`「两个学习统计合并成一个页面，用 tab 区分题库 / 英语」 | ✅ 已实现 |

**没有一件是"半成品"。** 用户说"错了"，指的是**它们没帮上比赛**，不是它们没做完。

### 2.2 但用户的直觉抓住了一个真问题

我数了提交分布（近 200 次提交，2026-10-13 至今）：

```
agent        23 次
practice     19 次
english      19 次   ← 最近 25 条提交里有 17 条是 english
studio       16 次
ai            9 次
mock-exam     7 次
```

**最近一次开发日（10-26），22 条提交里 17 条在打磨英语听写页的样式与模式。**

这就是用户烦躁的根源：**工程在往"功能广度"走，比赛需要的是"单点深度"。**
英语模块做得再完整，它是一个**第二个产品**，不是**第一个产品的卖点**。

### 2.3 判定

> **「之前的修改方向都错了」——这句话是错的。**
>
> **但「我们缺一个能一句话说清的卖点」——这个判断是对的。**
>
> 准确的说法是：**底座已经够了，叙事没串起来。**

具体一点：

- 诊断引擎（`study_diagnosis_service.py`, 824 行）是**真硬货**：SM-2 复习窗口、优先级打分、逐题建议、计划落库。我实跑 `diagnose(db, 1)` 返回 8 条逐题诊断，结构完整。
- 但它的**唯一出口是 Agent 工具**（`learning_stats.py:368` `diagnose_report`），**没有任何页面能直接打开它**——我查了所有 API 模块，`diagnosis` 相关路由**零命中**：
  ```
  GET /diagnosis/report  → {"code":200,"msg":"操作成功","data":null}   # catch_all 假 200
  ```
- 也就是说：**最硬的功能，藏在最难被看到的地方。**

**这才是真问题**：不是功能不够，是**最强的功能没有舞台**。

## 三、「绝对亮点」够不够格

### 3.1 先看用户的话术里，哪一句站不住

> 「别人只能把文件变成聊天框里的文字，我们能一键生成带精准表格、复杂公式、图文混排的原生 Word/PDF」

**这句话的漏洞**：前半句不是事实。

- 市面上的文档 AI 产品**早就能导出带格式的文件**（导出为 Word/PDF 已是基线能力），不是"只能聊天框里的文字"。
- 这句"别人只能……"是**自己立的靶子**。评委只要用过任意一个同类产品，这句话当场失效，还会连带怀疑后面的数据可信度。

### 3.2 差异必须换维度：从"能不能生成"换成"生成得准不准、能不能改"

真正站得住的差异，我按"可演示、可验证"的标准筛了三条：

| 差异 | 可验证方式 | 代码依据 |
|---|---|---|
| **① 闭环保真**：解析出的表格/公式，一路保真到导出文件，不退化成竖线 | 同一份 Word 导入→导出，原表 4×4，导出后仍是 4×4 真表格 | 当前**做不到**（已实跑证明），做成即为硬差异 |
| **② 脏数据修复**：修 Word/WPS 导入时坏掉的 LaTeX 控制字符残骸 | 输入含 `<TAB>imes` 的坏公式，导出后是正确 `×` | `bank_export_service.py:71-87` 已有实现 |
| **③ 可编辑而非贴图**：公式是 OMML 原生对象，不是图片 | 在 Word 里双击公式可直接编辑 | `mathml_omml.py` + `_add_omml`（:558） |

**注意**：① 是缺口，②③ 是已有能力。
→ **补齐 ①，②③ 才有资格被讲出来。** 现在讲 ②③，等于承认"我们的表格是烂的"。

### 3.3 三个更强的候选（全部基于已有代码，不画饼）

> 判断标准：**必须复用现有资产**，且**2 周内一个开发者能做出来**。

#### 候选 A：「错题 → 复习计划 → 可直接打印的卷子」一键闭环 ⭐ 推荐

**为什么强**：把三个**已存在但分散**的能力串成一条线，是"闭环"这个词唯一一次被真正兑现。

现状（都已实现，只是没连起来）：
```
study_diagnosis_service.diagnose()   → 算出 40 道错题的分档与优先级（实跑 OK）
study_diagnosis_service.persist_plan → 把复习间隔写回错题本（实跑 OK）
bank_export_service.export_bank_docx → 导出卷子（无答案版已有，:695）
learning_stats.diagnose_report       → 诊断报告 PDF（实跑 113KB OK）
```

缺的只是一步：**按诊断结果筛题 → 组一张复习卷**。

- **工作量**：一个"按 level 筛题 + 调用既有导出"的 API，约 1~2 天；前端一个按钮，约 1 天。
- **演示画面**：点「按薄弱点生成复习卷」→ 3 秒后下载下来一份 Word，标题写着"根据你 40 道错题中最该处理的 8 道生成"。
- **为什么比表格强**：表格是**修缺陷**，这是**新能力**。缺陷修好没人鼓掌，新能力会。

#### 候选 B：「一份资料 → 一张知识树」—— 解析结果结构化成思维导图

**为什么强**：它让"RAG 知识库"这件抽象的事**第一次有了画面**。

现状：
```
file_parser 按标题/段落分块，保留章节层级（:48）
rag/chunker.py 分块 → 向量化 → 入库
```

层级结构**已经在数据里**，只是从未被可视化。把树画出来即可，**不需要 LLM**。

- **工作量**：一个把 chunk 层级转成树的前端渲染（SVG/DOM 手写，无需引入 mermaid——项目没有该依赖），约 3~4 天。
- **注意**：**别叫它"实时生成"**。用已有层级渲染是**零延迟、零幻觉**的，这反而是优点——"不是 AI 编的，是你的资料本来的结构"。这比"边说边长"更可信。
- **局限**：它证明的是"解析质量"，不是"AI 能力"，创新性得分中等。

#### 候选 C：「学情诊断报告」从 Agent 工具升级为一等公民页面

**为什么强**：把**最强的算法**从聊天气泡里放出来。

现状（我实跑验证）：
```
diagnose(db, user_id=1, limit=20) → hasData=True, items=8,
  keys=[hasData, generatedAt, summary, items, byLevel, bySubject, activity, headline, suggestions]
export_diagnosis_pdf(diag)        → 113,282 bytes ✅
Agent 工具 diagnose_report        → 可下载 PDF ✅
```
**但没有任何页面能打开它。**

- **工作量**：一个页面 + 一个只读 API，约 2~3 天。加日历视图（学习规划表）再 2 天。
- **演示画面**：点「学情诊断」→ 出一份带分档、逐题建议、复习日历的报告，可导出 PDF/Word。
- **为什么强**：这是**唯一一个"算出来的"而不是"生成出来的"**功能。评委问"AI 是怎么编的"时，你能回答"这部分不是编的，是算的"。这一句在答辩里值很多分。

**排序**：A > C > B（理由见第五节）

## 四、功能不够 vs 叙事不聚焦

### 4.1 判断：**叙事不聚焦**

证据：产品已经有 32 个 API 模块、156 个后端源文件（4.9 万行）、18 个 Agent 工具、8,482 行英语模块、一个 824 行的诊断引擎。

**这不是一个"功能不够"的产品。** 这是一个"**功能多到讲不完，于是每个都讲不透**"的产品。

再看用户自己写的文档里的分裂：

| 文档 | 定位 |
|---|---|
| `doc/CORE-FLOW.md:10` | "上传一份 Word/PDF/MD → 自动解析 → 变成你的题库 → 直接开刷" |
| `doc/ITERATION-PLAN.md:140` | 教师端 = ⚪ P3「更远」 |
| 用户现在的原话 | "围绕用户群体 **学生/教师**" |

**用户自己的迭代计划里，教师端是 P3；现在的新方向却把教师提到了主叙事。** 这不是方向变了，是**方向从来没定过**。

### 4.2 初筛的现实

`doc/competition/讲稿与答辩预案.md:30` 写着：

> 初筛 = 主观评分 + AI 评分，取前 20 名进线下路演。

**AI 评分读的是文字可读性，评委看的是第一印象。**

→ 一个"能一句话说清 + 有画面"的作品，在初筛里**碾压**一个"功能很多但讲不清"的作品。
→ 再加 5 个功能，只会让 PPT 的第 3 页更挤。

**判定**：**把已有能力讲成一个故事，对初筛更有效。**

### 4.3 唯一主线故事

#### One-liner

> **资料进，卷子出——中间那一遍一遍的活，AI 替你干了。**

（备选，更贴近"教师"定位：**"教师出一份卷子要 2 小时，我们把它压到 2 分钟，并且卷子里的表格和公式仍然能改。"**）

#### 三段支撑

**第一段：它能读懂你的资料（不只是抽文字）**
- 上传 Word/PDF/MD，公式（OMML + 裸 LaTeX）、图片、表格**都认得出来**
- 证据：`file_parser.py:667` 表格 → 标准 Markdown；`file_parser.py` OMML → LaTeX；图片按位置归属段落，正文留 `【图N】`
- 一句话：**"教材里最难搞的公式和表格，它认得出来。"**

**第二段：它知道你哪里不会（是算出来的，不是编出来的）**
- 基于 SM-2 复习窗口 + 逐题优先级打分，给出分档：反复失守 / 一做就错 / 欠复习 / 可以归档
- 证据：`study_diagnosis_service.py:290` `_classify`、`:339` `_priority_score`；实跑返回 8 条逐题诊断
- 真实数据：299 次作答、正确率 49.5%、40 道待消灭错题
- 一句话：**"这份诊断不是大模型生成的，是算出来的——同一份数据永远得到同一个结论。"**（这句话直接来自 `diagnosis_report_service.py:303-305` 的现有文案）

**第三段：它给你的是能直接用的东西（不是聊天记录）**
- 一键导出原生 Word / PDF：**表格是真表格、公式是能双击编辑的 OMML、图片在原位**
- 两种版本：教师卷（含答案解析）/ 学生卷（无答案 + 作答空行）
- 证据：`bank_export.py:142`、`:178`（schema 已写明 `native equations`）；`bank_export_service.py:695`（无答案版）
- 一句话：**"产物能被带走才叫功能，只能被读到只是回答。"**（这句话也直接来自 `diagnosis_report_service.py:10` 的现有文案）

> **为什么这三段是一条线**：读懂资料 → 找出不会的 → 产出可用的卷子。
> 它把**现有的全部硬资产**（解析、RAG、诊断、导出）串成了一句人话，且每一段都有代码和真实数据背书。
> **英语模块不在这条线上——所以它不是卖点，它是别的产品。** 这解释了用户为什么烦躁：他隐约感到了这件事，但归错了因（"方向错了"而非"这条线没被讲出来"）。

## 五、只做一件事做哪件

### 5.1 决定：把「原生表格 + 公式」贯穿 **解析 → 展示 → 导出** 全链路

**注意这个措辞**：不是"做一个表格导出功能"，是**修一条断掉的链**。

现状（已实跑证明）：
```
解析 ✅ file_parser._emit_table  → 标准 md 表格
展示 ✅ latex.ts 统一管线        → KaTeX 公式 + <table>
导出 ❌ bank_export_service      → 表格退化成 | --- | 竖线文本
```

**链在最后一环断了。** 而这一环恰恰是"能带走"的那一环。

#### 为什么是它，而不是候选 A/C

| 候选 | 为什么不是第一优先 |
|---|---|
| A（错题→复习卷闭环） | 很诱人，但它**建立在导出能力之上**。现在导出的卷子里表格是烂的，闭环越完整，烂得越明显。**先修路，再跑车。** |
| C（诊断报告页面） | 价值极高，但它是"**新做一个入口**"，不解决"已有能力自相矛盾"的硬伤。且它演示时是静态页面，冲击力弱于"下载一个 Word 打开"。 |

**排序逻辑**：
> 表格/公式全链路 = **修掉一个会让评委当场发现的自相矛盾**。
> 这个矛盾现在就存在：屏幕上表格是对的，导出的文件里是竖线。
> **只要评委点一次导出，你就完了。**

### 5.2 3 分钟演示分镜

> **前置准备**（演示前必须做完，否则 3 分钟变 5 分钟）：
> 1. 用 `user1` 登录（299 次作答、40 道错题，数据最全）
> 2. 准备一份**含表格 + 公式 + 内嵌图**的 Word（如概率论联合分布表）——这是唯一能同时打中三点的素材
> 3. 后端带 `--reload`，**提前跑一遍导出预热**（避免首次字体注册/模型冷启动）
> 4. 浏览器 100% 缩放、隐藏书签栏、关通知
> 5. **本机录屏兜底**（`讲稿与答辩预案.md:92` 已有此预案）

### 5.3 现在已经有题库导出 Word/PDF 了，做完到底多出什么

**这是最关键的问题，必须给准话。**

| 维度 | 现在（已实现） | 做完（多出来的） |
|---|---|---|
| 公式（Word） | ✅ 原生 OMML，可编辑 | **无变化** |
| 公式（PDF） | ⚠️ **Unicode 近似**（`a⁄b`、`‾A`） | ⚠️ **仍近似**（除非改走 HTML→无头浏览器，见 `v3-tech-feasibility.md`） |
| 图片 | ✅ 原位插入、等比缩放 | **无变化** |
| **表格** | ❌ **退化成 `| --- |` 竖线文本** | ✅ **真表格**：可选中单元格、可调列宽、跨页不断行 |
| 版式 | 一段一块流式排版 | 无变化 |
| 双版本 | ✅ 教师卷 / 学生卷 | 无变化 |

> **多出来的，只有「表格」这一项。**
> 公式在 Word 里早就对了；PDF 里的公式做完之后**依然是近似的**（这条别对外吹）。

> 你在 PPT 第 3 页写"直接可打印、可提交"，评委点了导出，看到一堆竖线——
> **那一瞬间，你所有的数字都会被重新怀疑一遍。**

## 六、用户群体判断

### 6.1 同时讨好学生和教师：**是错误**

三个理由：

1. **叙事会散**：现在的 PPT 第 3 页只有一条核心链路（`讲稿与答辩预案.md:103-106`）。加一个群体就要加一段，而"≤10 页"和"每页 ≤150 字"是硬约束（`PPT-V2-改造方案.md:62`）。
2. **初筛评的是"一句话能不能说清"**：两个群体 = 两句话 = 一句都说不清。
3. **产品已经偏了**：英语模块（8,482 行，19 次提交）就是"广度优先"的产物，用户自己已经烦了。

### 6.2 必须二选一：**选教师**

**核心理由（一条就够）**：

> **学生是终点消费者，教师是分发节点。**
> 教师用你的工具出卷 → 全班学生都要用 → 你拿到一个班级的数据。
> 学生自己用 → 只有一个用户。
> **评委问"怎么推广"时，教师侧的答案比学生侧强一个量级。**

**配套理由**：

- 导出原生可编辑文件这件事，**只有教师真的需要**（学生不需要改题）——你的技术强项正好命中。
- "可打印、可提交"这个话术，对教师是**日常场景**，对学生是**偶尔场景**。

### 6.3 教师需要、学生不需要的三条能力

| # | 能力 | 为什么教师需要 | 为什么学生不需要 | 现状 |
|---|---|---|---|---|
| **1** | **双版本导出 + 批量组卷**（教师卷含答案 / 学生卷无答案且留作答空行） | 出卷就是"一份自己看答案、一份发下去" | 学生只要刷题，不需要"无答案版" | ✅ 已实现（`bank_export.py:142` `:178`；`bank_export_service.py:695`） |
| **2** | **按知识点/难度/题型筛选组卷** | 教师出题有教学目标（"这次考第三章，难度中等"） | 学生跟着系统走即可 | ⚠️ 部分有（`MockExamSetup.vue` 有自定义组卷，但是**给自己考**，不是**给全班出卷**） |
| **3** | **班级维度的学情聚合**（看全班薄弱点分布，而非单个学生） | 教师的核心诉求是"这班哪块没学会" | 学生只看自己的 | ❌ **零命中**（我 grep 了 `教师\|老师\|班级\|组卷\|学情`，后端无班级/学生关系模型） |

> **诚实标注**：第 3 条是**真正的新工作量**（需要建班级/师生关系模型），不是 2 周能做完的。
> 但它**不影响主线**——主线（表格公式全链路）是教师侧的**必要前置**：
> 教师拿到的是一堆竖线，就谈不上"组卷给全班"。
