# 资料空间：任务链设计

## 1. 目标

让「上传 → 解析 → 切分 → 向量化 → 整理 → 应用 → 重新索引」成为一条可靠的单文档任务链，用户只在文档行看到当前状态，不新增任务中心之类的额外入口。

## 2. 单一状态源

不在前端维护第二套任务状态，文档状态仍以 `rag_document` 为准：

| status | 含义 | 前端展示 |
|---|---|---|
| 1 | 待解析 | 待解析 |
| 2 | 解析中 | 解析中 |
| 3 | 已解析未向量化 | 解析中 |
| 4 | 处理失败 | 处理失败 + 重新解析 |
| 5 | 已向量化 | 可检索 |

后端每次状态变化同步写：

- `status`
- `error_msg`
- `update_time`
- `chunk_count`（向量化完成后）

## 3. 单文档单飞

`document_pipeline.process_document(doc_id)` 增加进程内单文档锁：

- 同一文档同一时间只能跑一条流水线
- 重复触发直接返回 `duplicate=true`
- 上传、重解析、整理应用只复用已有任务，不重复消耗 embedding

后续如果要支持多进程部署，再把进程锁升级为 PostgreSQL advisory lock。

## 4. 异常恢复

服务启动时执行 `recover_stale_documents()`：

- 扫描 `status=2` 且 `update_time` 超过 15 分钟的文档
- 标记为 `status=4`
- 写入「处理中断（服务重启或任务异常），请重新解析」
- 不自动重跑，避免 embedding 不可用时批量打爆额度

## 5. 前端轮询

不新增任务中心。

- 上传成功后按返回的 `docId` 轮询 `/rag/document/status/{docId}`
- 应用整理后复用同一文档状态轮询
- 手动重新解析同样轮询
- 状态变为 4 或 5 后停止
- 文档行展示真实状态，失败时从「更多 → 重新解析」重试

## 6. 整理应用约束

`apply_plan` 只允许在 `status=ready` 时执行：

- 校验 `base_revision`
- 保存用户实际勾选的 `appliedChangeIds` / `appliedExclusionIds`
- 返回 `needsReindex`
- 由后端 `BackgroundTasks` 触发唯一一次重新索引
- 前端不再额外调用一次 `reprocessDocument`

## 7. 验收标准

- 同一文档连续触发上传/重解析/整理，只执行一条流水线
- 上传后状态能从 1/2/3 自动走到 5
- 应用整理后状态能从 2 自动走到 5
- 失败时 `status=4` 且有明确错误
- 服务重启后卡住的 status=2 文档会被标记失败
- 页面不需要任务中心也能看懂当前状态
