## 二、30 天：补主链路的短板

### 2.1 扫描版 PDF 接入 OCR 🔴 P0

**为什么最优先**：高校场景里，扫描版教材和真题是最常见的资料形态。现在传进去抽不出正文，检索基本失效 —— 等于这条资料白传了。

| 项 | 说明 |
|---|---|
| 现状 | `pypdf` 对无文字层的 PDF 只能抽出目录骨架（实测一份 500 页教材抽出 560 张整页图，72 个分块里只有 1 个关联到图） |
| 方案 | 前置版式检测区分「文字型 / 扫描型」；扫描型走多模态识图（复用项目已有的 `ocr.py`），逐页转文字后再入库 |
| 验收 | 扫描版教材上传后，能搜到正文内容；出题能引用原文 |

### 2.2 Markdown 图片解析 🟡 P1

`![](http://xxx/a.png)` 这类外链图现在不进知识库。补一个 Markdown 专用解析器，提取 `![alt](url)` 与 `<img>`，外链图可选下载入库。

### 2.3 知识库入库入口统一 🟡 P1

通过对话存资料（`knowledge_ingest` 工具）和通过页面上传，两条路径对图片的处理不一致。统一到同一个入口，避免「同样的文件，页面传有图、对话传没图」。

### 2.4 `/profile` 静态代理自检 🟡 P1

图片存为 `/profile/upload/...`，依赖 Nginx 反代。线上配置若漏了这条规则，图片全 404。部署检查清单加一项自动校验。

## 三、90 天：把「能用」做成「好用」

### 3.1 多模态向量：以图搜图 / 文字搜图 🟢 P2

**现状**：图片不参与向量化，只能「伴随文字被检索到」，不能作为检索目标。
用户说「帮我找那张电路图」是找不到的。

**方案**：引入图文同一向量空间的多模态模型（CLIP 系），或对每张图生成图注后再向量化；图片单独建索引，与文本索引做跨模态检索。

### 3.2 移动端适配 🟢 P2

现在主要是桌面端体验。补响应式布局与移动端交互（侧边栏抽屉化、输入区适配软键盘）。

### 3.3 对象存储直传（OBS） 🟢 P2

现在文件存本地磁盘，依赖 Nginx 静态代理。改为对象存储直传，彻底摆脱对本地目录的依赖，也便于多实例部署。

### 3.4 知识库与题库的「增量更新」 🟢 P2

教材改版后，现在只能整份重传。目标：只重传变更的章节，增量更新向量与题目，不动没变的部分。

## 四、更远：从工具到平台

### 4.1 校园版多租户

一个学校一个租户，教师可组卷、看班级学情；学生数据隔离。这是从「个人工具」走向「教学基础设施」的关键一步。

### 4.2 教师端组卷与学情分析

教师按知识点、难度、题型自动组卷；考完后看到班级维度的薄弱点分布，而不只是单个学生。

### 4.3 开放 API 与插件机制

题库、笔记、知识库开放 REST API，允许第三方接入（比如学校的教务系统、题库供应商）。

### 4.4 更多华为云能力接入

- **OCR**：扫描件识别（对应 2.1）
- **搜索**：大规模场景下的检索加速

## 五、已确认但不打算做

| 事项 | 为什么不做 |
|---|---|
| 诊断开药 / 医疗建议 | 合规红线，健康类只做台账辅助 |
| 从零生成整份课程 | 质量不可控，容易产出错误内容；我们的定位是「基于用户自己的资料」 |
| 全自动无人值守刷题 | 学习需要主动思考，代刷没有价值 |

## 七、技术债与工程质量

| 项 | 现状 | 计划 |
|---|---|---|
| 自动化测试 | 45 个探针（零 LLM 成本） | 补齐前端 E2E，接入 CI |
