# 开发过程记录

本目录存放 OpenStudy 项目开发过程中由开发工具产生的原生记录，用于说明开发方式。

> 这些文件是**工具自动产生的原始记录**，不是事后编写的说明文档。
> 时间戳、会话 ID、事件序列都可以和代码提交历史对照。

---

## 目录内容

| 目录 | 内容 | 来源 | 大小 |
|---|---|---|---|
| `logs/` | 每日开发日志（5 个） | 开发工具运行时日志 | 11 MB |
| `sessions/` | AI 辅助代码分析会话（6 个） | 工具会话记录导出 | 79 KB |
| `memory/` | 开发决策与踩坑笔记（91 个） | 工具长期记忆导出 | 612 KB |
| `codebase/` | 代码库索引记录 | 工具索引库导出 | 2 KB |

## 一、`logs/` —— 每日开发日志

**文件**：`experience-2026-10-08.log` ~ `experience-2026-10-12.log`

**这是什么**：开发工具在运行期间逐条写下的日志，每天一个文件。记录内容包括：
会话创建、消息处理、记忆检索、项目配置加载等。

**能说明什么**：
- 2026-10-08 至 2026-10-12 期间，工具在本项目上持续工作；
- 日志里有 `session.created` / `chat.message` 等事件，可以和 `sessions/` 里的会话对得上；
- 每天的事件密度不同（10-11 最密集，1.5 万行），反映开发强度的真实分布。

**已做的脱敏**（不改变内容语义）：
- 本地绝对路径替换为 `<PROJECT>` / `<TOOLHOME>` / `<USERHOME>`；
- 含赛事 / 评审等无关内容的行替换为 `<本行内容已按隐私策略省略>`（共 5 行）；
- 疑似密钥替换为 `<SECRET>`（共 231 处）。

> 说明：日志本身**不含对话正文**，只有事件与摘要字段。之所以仍有上述脱敏，
> 是因为部分 `query=` 字段会截取用户提问的开头一小段。

## 二、`sessions/` —— AI 辅助代码分析会话

**文件**：6 个会话，每个是一次完整的「AI 分析代码库 → 给出定位结论」过程。

| 文件 | 消息数 | 工具调用 | 内容 |
|---|---|---|---|
| `01-梳理项目智能体功能.md` | 118 | 53 | 全项目智能体相关代码盘点 |
| `02-调研多智能体改造可行点.md` | 81 | 43 | 评估多智能体改造的技术可行性 |
| `03-定位题库AI搭建图片处理.md` | 109 | 36 | 定位文档图片处理链路断点 |
| `04-定位智能体文档解析图片处理.md` | 136 | 44 | 定位知识库入库时的图片丢失 |
| `05-定位题干渲染点与LaTeX表格支持.md` | 124 | 44 | 找出题干渲染未用公式组件的页面 |
| `06-排查前端题目链接TAB来源.md` | 143 | 55 | 排查表格竖线被转成制表符 |

**为什么这些能证明开发过程**：
- 每个会话都有**真实的会话 ID**，与 `logs/` 里的事件一一对应；
- 用户提问是**针对真实代码位置的追问**（例如「`registry.py` 的 `definitions(exclude=...)` 是否支持裁剪」），
  不是泛泛而谈；
- AI 的工具调用记录显示它**实际读了文件**（`read` / `grep` / `glob`），不是凭空回答。

**已做的脱敏**：
- 项目的本地绝对路径替换为 `<PROJECT>`；
- 含无关内容的段落替换为 `<该段内容已按隐私策略省略>`。

## 三、`memory/` —— 开发决策与踩坑笔记

**文件**：91 个 markdown，每个记录一个具体的技术决策或踩过的坑。

**这是什么**：开发工具在长期协作中沉淀的项目知识。每条都带 `Why` / `How to apply`，
记录的是「为什么这么做」而不是「做了什么」——这部分恰好是代码本身看不出来的。

**典型例子**：

| 文件 | 记录了什么 |
|---|---|
| `feedback-latexrenderer-vhtml-needs-nonscoped-table-style.md` | scoped CSS 无法作用于 v-html 内容，必须用非 scoped 样式块 |
| `feedback-marked-table-latex-pipe-conflict-and-endtoend-testing.md` | Markdown 表格竖线与 LaTeX 公式的冲突及测试方法 |
| `project-chat-first-token-latency.md` | 首字延迟的完整排查过程与优化手段 |
| `project-agent-tools-reframe-as-experts.md` | 「工具」改造成「专家」的产品决策依据 |
| `feedback-git-worktree-isolation.md` | 用 git worktree 隔离改动的工作流 |

**为什么这些有价值**：这些是**真实踩坑的记录**，不是设计文档的复述。
比如「思考流式卡死真因是改了 raw 对象不触发 Vue 更新」这种结论，
只能从实际调试中得到。

**已做的脱敏**：
- 项目的本地绝对路径替换为 `<PROJECT>`；
- 5 个文件因涉及赛事材料准备被整份排除（见下）；另有 14 个文件因内容涉及
  同类话题被排除。**排除的这 19 个文件不在本目录内。**

## 四、`codebase/` —— 代码库索引记录

**文件**：`index-report.md`

**这是什么**：开发工具的代码库索引库（`file-index.db`）的可读摘要。

**为什么交摘要而不是原始库**：原始库是 564 KB 的 SQLite 二进制，评审无法直接阅读。
摘要里给出了登记文件数、目录分布、类型分布等可核对的信息。

> ⚠️ **这份记录有局限，要说清楚**：
> 索引库登记了 1126 个文件，但任务状态全是 `pending`、`success` 计数为 0。
> 也就是说**索引任务被创建了但没跑完**。
> 它能证明「做过索引操作」，**不能**证明「全库索引已完成」。
> 详见 `codebase/index-report.md` 第二节。

## 六、关于这些记录能证明什么、不能证明什么

**能证明的**：
- 开发工具在本项目上真实运行过，有连续 5 天的日志；
- AI 参与了实际的代码定位与分析工作，有带会话 ID 的完整记录；
- 工具对本仓库做过索引操作。

**不能证明的**：
- 不能证明全部代码都由该工具生成 —— 项目前期有其他开发方式，这一点不回避；
- 不能证明索引任务已完成（见上）。
