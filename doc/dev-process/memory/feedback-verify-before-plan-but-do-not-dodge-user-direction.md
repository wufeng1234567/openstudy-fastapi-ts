**用户对 bug 的归因与 Agent 的实测结论矛盾时：先核代码/实测现状（不臆断），同时不要否定用户对 UI 的直观判断；在澄清归因的一句话后照常推进方案，不要卡在"谁对"上。**

**Why:** 2026-10-12 用户说「问题不在深度思考，在于添加模型那边没写好」，但 Agent 上轮实测已证 `reasoning_effort` 修复让 magpie 出深度思考（用户自己也回了"有深度思考了"）。Agent 的处理是：先声明"这个 tab 方案我会写成文档、今晚不动代码"，再**明确点出归因分歧**（"你说问题在添加模型那边，但实测深度思考已修复，所以新需求的本质是产品可用性/语义划分而非深度思考坏了"），随后**照常核对前端现状并出方案**。该处理被用户接受，未引发争论。

**How to apply:**
- 先做：读代码/实测核实现状（见 `feedback-verify-code-not-memory-before-plan`）。
- 再做：若用户描述与实测不符，**坦率但简短地指出**（一句话），并把用户需求重述为其真正本质（此处=区分服务商的产品语义需求，非"深度思考坏了"）。
- 禁止：既不盲从用户归因去改错方向，也不因"用户说错了"而拖延/拒绝产出方案；澄清与推进要**同时**发生。
- 该条是对 `feedback-verify-code-not-memory-before-plan` 的补充（核实现状 ≠ 顶回用户方向），非替代。
