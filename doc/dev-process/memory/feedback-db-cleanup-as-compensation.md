当 DB 中存在的偏好/配置数据是**用户 UI 根本无法产生的残留（旧面板 bug 产物）**时，**清掉这份脏数据是修复的既定组成部分，不必反复向用户征求"是否允许改库"的同意**。

**Why:** 2026-10-11 排查子代理工具集为空，Agent 一度纠结"直改用户 DB 属高风险操作、是否先问用户"，但用户已明确表示"**要我自己干**""**去拿信息**"→ 已授权自己动手。且待删的是**与用户陈述一致的明确脏数据**（`user_id=105` 的 12 条全量 `disabled=1` 残留），不是用户的真实配置。此前 `project-subagent-user-disabled-rootcause-confirmed` 也已把"清数据"列为修复第二层。

**2026-10-11 二次适用（清「误建的真实草稿笔记」— 已完成）**：用户对「库中早期误建的草稿笔记要不要清」的遗留直接答「**清理掉吧**」——再次印证：凡删的是「用户 UI 无法产生 / bug 产物 / 用户贴切描述为误建」的明确脏数据，**直接干、不必再问一轮**。**已执行完毕**：user 105 于 10-10 建的 7 篇（438 C++／439 Spring Boot／440 Python／441 数据结构／442 计算机网络／443 Java／444 MySQL）全部**软删**（`del_flag='2'`）；`136`/`384`/`39`（user 1）**未碰**。

**白名单校验的正确口径（踩坑教训）**：校验应放宽为「**标题含'速记'**」或**直接按 id 白名单**；**勿**把标题精确写成"以'核心知识点速记'结尾"——实测 `439` 标题实为「Spring Boot **核心注解速记**」（不含"知识点"二字），过严的正则会在第一轮把整批拦下、一篇不删（`严格 id 白名单 + 前置校验、不通过就整体不删` 是安全设计，但标题特征须写对）。

**How to apply:**
- 清数据前先**备份查询 + 精确限定范围**（只删目标 user 的禁用残留记录），不要广域 DELETE。
- 若目标是「真实业务行」（如笔记），优先用**逻辑删除（软删）而非硬删**：与系统删除行为一致、可恢复、更安全；并先**列出精确待删集合（id 白名单）**再动手。
- 删除动作仍按高风险对待：能同步（psycopg2）就别走沙箱 asyncio（本环境 asyncio 建不起来，见 `feedback-sandbox-blocks-asyncio-event-loop`）。
- 与 `feedback-do-not-a<SECRET>` 一致：这不是"两条互斥路径"的技术分叉，而是**已定策的执行项**——直接干，不要为"要不要清"再问一轮。
