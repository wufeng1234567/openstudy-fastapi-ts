## 一、结论摘要

智能对话的主发送链路可以正常走通：真实模型调用、SSE 事件、工具调用、消息落库、时间线快照、删除会话清理均已验证通过。

但当前不能判定“用户闭环完成”：

1. **后端遗留的 `GET /ai/conversation/{session_id}` 路由没有注册**，请求被 `catch_all` 兜成 `HTTP 200 + data:null`。前端普通会话历史读取会静默得到空列表；全局悬浮助手（AiAssistant）的普通聊天模式、以及任何没有时间线快照的会话，历史会不可见。真实测试中数据库已有 user/assistant 两条消息，浏览器接口却返回 `data:null`。
2. **会话相关写接口缺少会话归属校验**：任意登录用户只要拿到另一个用户的 `sessionId`，就可以覆盖对方的时间线快照、向对方会话追加消息。真实测试已复现：user2 覆盖 user1 的时间线后，user1 重新读取看到的是 user2 写入的内容。

因此该模块当前是 **“单次聊天可用，但历史恢复和跨用户数据隔离不闭环”**。

## 三、P0 问题

### P0-1：`GET /ai/conversation/{session_id}` 路由缺失，历史接口静默返回空

**现象**

- 后端 `openstudy-fastapi/app/api/v1/ai.py:1527` 定义了 `async def get_conversation(...)`，但函数前**没有 `@router.get("/conversation/{session_id}")` 装饰器**。
- `openstudy-fastapi/app/api/v1/catch_all.py:13-14, 32` 会把未匹配的 API 请求兜底成 `{"code":200,"msg":"操作成功","data":null}`。
- 因此 `GET /ai/conversation/{sid}` 匹配不到 GET 路由，回落到 `catch_all`，返回 200 + null，而不是 404 或真实历史。
- 后端既有 E2E `tests/e2e_agent_api.py:1790-1795`（G5）明确期望「读别人会话 → body.code=403」；当前会命中 catch_all 得到 `code:200`，说明该装饰器是被改动时漏掉的，不是有意下线。

**真实证据**

- 普通助手测试：先用 `/ai/assistant/stream` 发送 `audit_纯文本助手历史测试...`，数据库 `ai_chat_message` 明确有：
  - `user | audit_纯文本助手历史测试...`
  - `assistant | audit_plain_ok`
- 随后 `GET /ai/conversation/asst_1793617973574_a46b1c` 返回：
  - `{"code":200,"msg":"操作成功","data":null}`
- OpenAPI 的 `/ai/conversation/{session_id}` 只有 `delete` 方法，没有 `get` 方法。

**用户影响**

- 全局悬浮助手 `AiAssistant` 的 `loadMessages()` 每次都调用 `getConversationHistory()`（`openstudy-vue3-ts/src/components/AiAssistant/index.vue:957-966`）。
- 返回值是 `{code:200,data:null}`，类型判断 `Array.isArray(histRes.data)` 为 false，历史被当成空数组。
- 用户刷新页面、切换旧会话、普通聊天模式或重新打开没有时间线快照的会话后，**看到的是空对话**；数据库里的历史并没有丢。
- 在 `AiAssistant` 中当前会话 `messages.length === 0` 时，新建会话还会走“复用当前空会话”的分支（`index.vue:990-1000`），可能出现“点新建对话没反应”的次生问题。
- 智能对话页 `chat.vue:955-956` 的 ordinary fallback 同样失效；当前只有保存了时间线快照的会话能通过快照恢复。

**根因**

`get_conversation` 函数是从旧路由迁移/重排时遗漏了装饰器；同时仓库的 `catch_all` 对任何未匹配 API 返回 200，掩盖了路由缺失。

**建议修复**

1. 在 `ai.py` 的 `get_conversation` 上补：
   ```python
   @router.get("/conversation/{session_id}")
   ```
2. 修复后补一条接口级测试：写入两条消息 → GET 返回 `List`，而不是 `null`。
3. 评估 `catch_all`：至少对 `/ai/*` 未匹配路径返回 404，避免后续路由缺失继续静默假成功。

### P0-2：会话相关写接口没有归属校验，可跨用户覆盖时间线 / 追加消息

**现象**

- `PUT /ai/conversation/{session_id}/agent-timeline` 接收 `userId`，但 `conversation_service.save_agent_timeline()`（`conversation_service.py:674-717`）只按 `session_id` 查行，**不校验 `row.user_id` 是否是当前登录用户**；行存在就直接覆盖 `payload`。
- `POST /ai/conversation/{session_id}/messages` 调用的 `save_turn()`（`conversation_service.py:322-427`）同样不校验会话行归属；会话行存在时直接追加消息并累加 `message_count`。
- `save_message()`（`conversation_service.py:255-319`）也是同样口径。

**真实证据**

测试会话：`asst_1793617892124_d00c73`

1. user1 创建会话并写入首条消息（会话行 `user_id=105`）。
2. user2（uid=106，登录 token 正常）调用：
   - `PUT /ai/conversation/asst_1793617892124_d00c73/agent-timeline`，body 写入 `audit_attacker_timeline`
   - 响应 `code=200`
3. user1 再读时间线，内容变成 `audit_attacker_timeline`。
4. user2 再调用 `POST /ai/conversation/asst_1793617892124_d00c73/messages`，响应 `code=200`。
5. DB 结果：
   - `ai_chat_session` 仍是 `user_id=105`，但 `message_count=4`
   - `ai_agent_timeline` 的 payload 已是 user2 内容
   - `ai_chat_message` 同时存在 `user_id=105` 和 `user_id=106` 的行

**用户影响**

- 知道/猜到 `sessionId` 的其他登录用户可以篡改对方看到的对话时间线内容；如果写入恶意内容，至少造成会话内容污染；消息注入还会破坏会话计数与历史一致性。
- 会话 id 是 `asst_<毫秒>_<6位hex>`（`conversation_service.py:84-86`），不是高熵秘密，不能作为唯一权限凭据。
- 这是安全/数据一致性问题，不能以“前端正常不会传别人的 id”来忽略。注意：子代理 A 的“越权通过”只覆盖了 `?userId=他人` 参数，未覆盖路径里的 `sessionId`；本项是本代理补测发现的。

**建议修复**

- 在 `save_agent_timeline`、`save_turn`、`save_message` 里统一做：
  - 若 `ai_chat_session` 已存在且 `user_id != 当前 uid` → 拒绝（403 / 明确错码）；
  - 若不存在 → 只允许以当前 uid 创建；
  - 禁止在 `update` 时把他人行当作无主行覆盖。
- 时间线 `PUT` 端点增加显式 403 测试；`POST messages` 增加跨用户测试。

## 四、P1 / P2 问题

### P1-1：时间线快照保存是前端主动 `PUT`，服务端不保证快照存在

- `useAgentChat.send()` 在 `finally` 里调用 `saveAgentTimeline`（`useAgentChat.ts:1737-1751`），如果用户关闭页面、网络中断或 `saveAgentTimeline` 失败，只有 `ai_chat_message` 落库，时间线快照缺失。
- 此时 `chat.vue` / `AiAssistant` 会回退到 `getConversationHistory`；由于 P0-1 该接口又是空的，用户会表现为“历史上明明聊过，刷新却没有”。
- 即使修复 P0-1，也建议后端在流结束时兜底保存一份时间线，或前端在 `beforeunload` / 发送完成时保证至少写入普通消息。

### P1-2：SSE 事件契约文档漏掉 `tool_confirm` / `tool_confirm_resolved`

- `app/services/ai/agent/loop.py:14-28` 的事件契约表列了 `meta` / `text` / `thinking` / `waiting` / `tool_start` / `tool_result` / `self_correct` / `metrics` / `warning` / `error` / `done`，但没有 `tool_confirm` 与 `tool_confirm_resolved`。
- 实际实现会在 `loop.py:2157` / `2170` 下发这两个事件，且前端确认卡片完全依赖它们；契约文档漏项会让后续维护者漏发/漏消费，用户表现为「该确认时没有卡片，任务卡住」。
- 建议补齐事件表及载荷字段（`confirmId` / `tool` / `action` / `params` / `preview` / `destructive`）。

### P1-3：`/ai/agent/tools`、`/ai/agent/roles`、`/ai/agent/configs` 使用裸对象，与全局信封不一致

- 同一模块的 `/ai/sessions`、`/ai/conversation/*` 返回 `{code,msg,data}`，但 `/ai/agent/tools` 返回 `{"tools":[...],"actions":{...}}`、`/ai/agent/roles` 返回 `{"roles":[...]}`、`/ai/agent/configs` 返回 `{"agents":[...]}`。
- 统一封装/文档缺失会让新调用方按 `res.data.tools` 取数时拿到 undefined（本次检查子代理也先按统一信封解析后误判为「工具全空」，复核才纠正）。
- 建议统一走 `success()`，或在前端 API 层集中封装并注释特例。

### P1-4：错误事件可能重复提示

- `postAgentStream` 在 `emit()` 中对 `event.type === 'error'` 调用了 `onError`（`agent.ts:596-600`）；
- `useAgentChat.send()` 同时传入 `onError: (msg) => pushNote('error', msg)` 和 `onEvent: handleEvent`（`useAgentChat.ts:1650-1653`）；
- `handleEvent` 的 `case 'error'` 又调用 `pushNote('error', ...)`（`useAgentChat.ts:1512-1518`）。
- 因此如果后端发 SSE `error` 事件，界面可能同时出现两条同样的红色错误 note。建议只在 `handleEvent` 里统一处理，`onError` 只用于网络/HTTP 层错误。

### P2-1：`/ai/agent/execute` 注释与实现不一致

- `ai.py:735-743` 的 docstring 写“本接口不接受 `turn_id`”，但 `AgentExecuteRequest` 已在 `ai.py:708` 定义 `turnId`，`ai.py:775` 也把它传给 `execute_agent_tool`。
- 注释是过期说明，容易误导后续维护者；建议同步更新。

### P2-2：新建会话的注释仍是旧语义

- `chat.vue:911` 和 `agentSession.ts:202` 写“后端立即落一条空会话”，但 `ai.py:1765-1792` 的实际实现是“只生成 id，不写库”。
- 当前行为本身更好（避免空壳会话），只是注释过期。

### P2-3：会话删除未清理回退账本 / 上传附属数据

- `delete_session()`（`conversation_service.py:177-206`）删除消息与时间线，但未删除 `ai_agent_op_log` 中该会话的回退账本，也未清理 `chat_upload` 相关附件。
- 这些数据通常不可见，但会留下孤儿行/文件，长期运行需要清理策略。

### P1-5：未登录可直接进入 `/front/agent/chat`，发送入口没有登录兜底

- `permission.ts:15` 的 `whiteList` 包含 `/front/agent/chat`；无 token 时 `permission.ts:232-234` 直接 `next()` 放行，绕过了路由 meta 的 `requiresLogin`。
- 进入后 `chat.vue:1146-1153` 在 `userId` 为空时仍会 `createSession(undefined)`，失败则使用本地 `asst_${Date.now()}` 继续发送；用户可能看到空页面或收到不友好的发送错误，而不是被引导登录。
- 前端子代理 B 未实测游客具体表现（时间不足），但代码路径明确存在。建议：白名单仅限只读浏览，发送前 `ensureLogin`；或从白名单移除该路径并在路由守卫弹登录。

### P1-6：AiAssistant 空会话复用判断会被历史加载失败放大为“新建无反应”

- `AiAssistant/index.vue:996` 判断 `currentSessionId` 存在且 `messages` / `agentMessages` 都为空时，视为当前仍是空会话，只 `loadSessions()` 不新建。
- 由于 P0-1 会让有内容的普通会话历史读成空数组，此时用户点“新建会话”会被误判为复用空会话，看起来没有反应。
- 建议增加“历史已加载完成且确实为空”的显式标记，或修复 P0-1 后复核该路径。

### P2-4：`/ai/agent/rollback` 不校验空 `sessionId`

- `ai.py:2048-2051` 只校验 `turnId` 非空；实测 `POST /ai/agent/rollback {sessionId:"", turnId:"t_audit_002"}` 返回 `{"code":200,"data":{"reverted":0,"skipped":[],"failed":[],"partial":[]}}` 的成功形状。
- 对照 `POST /ai/conversation/drop-turn`（`ai.py:1664-1669`）两个字段都校验并回 `code=400`；这里是同一类「空 sessionId 静默返 0」风险。
- 建议照 `drop-turn` 补 `if not session_id: return error("缺少会话 id（sessionId），无法回退", code=400)`。

### P2-7：前端其它边界（子代理复核）

- 流式生成中刷新页面：本轮快照只在 `send()` 的 `finally` 写入（`useAgentChat.ts:1739-1751`），生成过程中刷新会丢本轮；建议 `beforeunload` 或在流事件中周期性写快照。
- `chat.vue:971` 生成中 `switchSession` 静默 `return`，而侧栏 `watch`（`chat.vue:988`）会先 `stop()` 再切换，两条切换路径行为不一致，用户可能点击无反馈。
- `createSession` 失败时本地伪造 `asst_${Date.now()}`（`chat.vue:1149-1151`、`AiAssistant:1004`），该 id 不在会话列表，刷新即丢；应至少提示并阻止发送。
- 移动端仅覆盖 720px hero 适配（`chat.vue:1824`），输入区/消息区窄屏未完整验证。

### P2-6：前端清理项（子代理 B）

- `chat.vue:1008-1027` 保留了一份旧的 `removeSession`，与侧栏 `agentSession` store 的删除逻辑双轨，当前模板若不再使用即为死代码，容易在后续误调用时多建一条会话。
- 会话列表仅支持删除，不支持重命名（FrontSidebar/index.vue:196-204）；不影响主闭环，属于体验缺口。
- `startNewSession` 每次点击都会生成新的 `sessionId`（虽然 `POST /ai/sessions` 不写库，不会产生空行），连续点击会产生无意义 id；可在前端复用当前空会话。

### P2-5：`catch_all` 对未知 API 统一假 200

- `catch_all.py:23-32` 对 `list` / `all` / `count` / 其他路径分别返回空数据或 `success(None)`。
- 这会把“路由写错、方法写错、前后端路径漂移”全部伪装成成功；本模块的 P0-1 就是直接受害者。
- 建议至少对 `/ai/`、`/rag/`、`/question*` 等已实现业务前缀返回 404；保留 catch-all 只给历史兼容接口。
