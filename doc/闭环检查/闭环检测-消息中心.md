## 一、结论摘要

消息中心页面可用：

- 顶栏/侧栏消息入口可进入 `#/front/messages/notifications`；
- 菜单显示系统通知、回复与@（未读 2）、分享通知（未读 8）；
- 系统通知页有加载/空态；分享通知 `/notification/notification/myList` total=10、未读 8；`/system/notice/listAll` 当前 user1 可见 3 条用户通知；
- 未登录接口返回 401；跨用户 markRead/delete 被忽略，不能删他人通知。

但存在阻断性安全问题与两个 P1：

1. **后台公告写接口无管理员鉴权**：`notices.py:370/393/423` 的 create/update/delete 只依赖登录用户，任意普通用户可发布/篡改/删除全站公告；`delete_notices` 直接物理删除全局行。这是 P0 越权写。
2. **`sys_notice.create_time` 22/25 行为 NULL**：评论/回复/@ 通知时间为空；`ORDER BY create_time DESC` 把 NULL 排最前，导致无时间旧消息压在新公告前；前端显示空白时间。
3. **两套通知通道未合并计数**：`/system/notice/unreadCount`=0，但 `/notification/notification/unreadCount`=7（分享通知）；只取任一接口都会漏算/多算。
4. **系统公告删除按用户隐藏且不可恢复**：user1 把 3 条系统公告删空后，`listTop` 永久为空；无恢复入口。
5. **分享通知删除/清空无二次确认**：直接调用删除/清空接口，误触即永久丢失全部分享通知。
6. **消息中心重复请求**：进入任一子页触发最多 3 次 `GET /system/notice/listAll`（layout + index + 子页），切 tab 再各来一遍；隐藏私信接口仍每次调用。

## 三、P0

### P0-1：后台公告写接口无管理员鉴权，普通用户可发布/篡改/删除全站公告

- `notices.py:370-390` `POST /system/notice`、`:393-420` `PUT /system/notice`、`:423-433` `DELETE /system/notice/{ids}` 都只 `Depends(get_current_user)`，没有 `require_admin` 或角色判断；`delete_notices` 直接 `delete(SysNotice)`。
- 任何登录用户（user1/user2）都可以调用这些接口发布/删除全站公告；前端后台菜单权限无法阻止直接 API 调用。
- 影响：越权内容投送/删除全站公告，属于 P0 安全与数据破坏风险。
- 建议：三个接口加 `require_admin` 依赖；前台删除只允许走 `/front/*` 路径；补充普通用户调用 403 测试。

## 四、P1

### P1-1：`SysNotice.create_time` 大面积 NULL，时间显示/排序错乱

- DB `sys_notice` 25 行中 22 行 `create_time IS NULL`（全部评论/回复/@ 通知）；API `listAll` 返回 `"createTime":null`。
- 根因：`SysNotice.create_time` 模型无 `server_default=func.now()`（`models/notice.py`），`notes.py:1201` 创建通知时也不传时间。
- 影响：消息列表时间空白；PostgreSQL `ORDER BY create_time DESC` 把 NULL 排最前，无时间旧用户通知会压住新系统公告（实测 user2 顺序 73,74,71,12,2,1）。
- 建议：模型加 `server_default=func.now()` + 写入侧 `datetime.now()` + 历史回填；排序 `nullslast()`。

### P1-3：分享通知删除/清空无二次确认

- 前端子代理实测 `shareNotices.vue:110-118` 删除、`:130-138` 清空均直接调用接口，没有 `ElMessageBox.confirm`；同为消息中心的系统通知/回复与@页面都有确认。
- 影响：分享通知页误触删除/清空即永久丢失；`clearNotifications` 是全量清空，不可恢复。
- 建议：与另两页对齐，删除/清空前加确认；清空文案明确数量。

### P1-2：两套通知通道未合并，红点/未读数可能漏算

- `/system/notice/unreadCount` 仅统计 `sys_notice`（user1=0），`/notification/notification/unreadCount` 统计分享通知（user1=7）。
- 消息中心页面分别显示系统 0、分享 8；但顶栏/第三方若只读一个接口会漏算。`layout/front.vue:281-301` 目前两路相加是正确方向，但 `messages/index` 也分别计算；接口层没有聚合未读。
- 建议：后端提供 `totalUnread` 聚合接口（sys + user_notification），前端红点统一使用。

## 五、P2 问题

### P2-1：系统公告删除按用户隐藏且不可恢复

- `notices.py:479-532` 对系统公告写 `sys_notice_delete` 只对当前用户隐藏；无撤销/恢复接口。user1 删除 3 条后 `listTop` 永久为空。
- 建议：消息中心提供“恢复隐藏的公告”，或删除前明确“仅对你隐藏且无法恢复”。

### P2-2：`listAll` 无分页 + HTML 原样返回 + 死代码风险

- `notices.py:250` 的 `listAll` 全量返回（当前 3 条，数据增长后性能/排序问题）；无分页。
- `notice` 内容 `<p>的撒大</p>` 原样返回；前端若 `v-html` 需确认有 DOMPurify。
- `notice_front.py:155/169` 的路由会真删全局 `sys_notice` 且无用户隔离；当前被 `notices.py` 先注册屏蔽，属于危险死代码，注册顺序一变即越权。
- 建议：`listAll` 分页；通知内容按纯文本或白名单清洗；删除/明确禁用 notice_front.py 冲突路由。

### P2-3：消息中心重复请求 / 已读失败静默 / 分页

- 进入任一子页触发 3 次 `/system/notice/listAll`（layout `fetchUnread`:287 + `messages/index` `fetchUnreadCounts`:96 + 子页 `fetchNotices`），切 tab 再各来一遍；隐藏私信 `getChatUnreadCount` 仍每次调用。
- `notifications/mentions` 的 `markRead/markReadAll` 失败 `.catch(()=>{})`，UI 已先置已读，刷新会回弹且无提示；建议失败回滚/提示。
- 分享通知固定 `pageSize=50` 无加载更多；系统/回复@全量 `listAll` 无分页；`createTime=null` 的 relativeTime 可能显示 1970-01-01。
- 建议：进入消息中心合并一次 listAll 分发；分享通知加正确错误态；统一时间无效值显示。

### P2-3：前端错误/分页细节

- 分享通知 `/notification/notification/myList` 固定 pageSize=50，无分页；超过 50 条无入口。
- `shareNotices.vue:90-94`、`messages/index.vue:112` 的 catch 静默，接口失败显示空态；建议错误提示/重试。
- `notifications.vue`/`mentions.vue` 删除/已读调用 fire-and-forget，失败仅 `ElMessage.error`，未回滚本地 read/delete 状态；刷新以服务端为准。
- 系统通知/回复与@ 页面无分页组件（数据量小时可接受）。
