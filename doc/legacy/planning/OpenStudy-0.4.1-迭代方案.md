# OpenStudy 0.4.1 迭代方案：资料知识网络

> 版本规范：本项目尚未发布 1.0，按语义化版本使用 `0.4.0 → 0.4.1`，不称 V4。
> 探索稿 · 2026-11-05
> 实现更新（2026-11-05）：0.4.1 的「知识地图」已替换为真正的实体-关系知识图谱；下文页面地图章节保留为早期设计记录，实际实现以发布说明和 `knowledge_graph_service.py` 为准。
> 参考：[WeKnora 产品介绍](https://weknora.weixin.qq.com/docs/01-getting-started/01-introduction)、[WeKnora Wiki 能力](https://weknora.weixin.qq.com/docs/03-features/14-wiki)、[WeKnora 知识库与知识管理](https://weknora.weixin.qq.com/docs/03-features/02-knowledge-base)、[WeKnora 文档解析](https://weknora.weixin.qq.com/docs/03-features/03-document-parsing)、[WeKnora 会话与对话体验](https://weknora.weixin.qq.com/docs/03-features/18-chat-experience)

## 一、先给结论

0.4.x 不建议继续在「资料装配」上堆同类能力，也不建议直接照搬 WeKnora 的 Go/docreader/Neo4j/MCP/多租户体系。

**0.4.x 的主线定为：把「我的资料」从文件列表，升级成可查找、可引用、可追溯、可再次使用的资料知识网络。**

四件事按这个顺序做：

1. **画廊**：先让所有图片、表格截图、独立图片变成可搜索、可描述的视觉资产。
2. **引用系统**：让人和 AI 都能在文档、笔记、题目、图片之间建立带原文位置的引用。
3. **知识图谱**：在引用与分块之上抽取实体-关系，做真正可追溯的知识图谱，不再做页面层级的「知识地图」。
4. **版本迭代**：把「AI 改了什么、前后差多少、能不能回退」讲清楚。

这个顺序很重要：**没有图片描述，画廊只是图片墙；没有引用数据，知识地图只是好看的节点图；没有版本对比，AI 整理就不够可信。**

## 二、WeKnora 值得学什么，不值得学什么

WeKnora 是腾讯开源的知识库问答系统，核心链路是文档解析 → 分块 → 混合检索 → 带引用回答；它有 Wiki、知识图谱、画廊、版本历史等能力。

### 2.1 值得学的能力

| WeKnora 能力 | 我们看到的价值 | 对 OpenStudy 的映射 |
|---|---|---|
| 知识库「画廊」 | 瀑布流展示文档图片；搜索图片描述和 OCR 文本；按来源文档筛选；点开看原图、描述、OCR 与来源 | **我的资料 → 画廊**：汇总当前资料夹 / 全部资料的文档图片、表格截图、聊天独立图片 |
| 图片处理流水线 | 文档解析出图片后，由 VLM 生成描述，按需 OCR；图片描述可作为索引内容 | **图片理解**：图片 + 所在章节 + 前后文一起交给视觉模型，不让模型「盲看一张图」 |
| 知识图谱 / Wiki 图谱 | 实体与关系抽取；按分组布局；聚焦、筛选、隐藏无关联节点；节点回到来源 | **实体-关系知识图谱**：LLM 从 chunk 抽取实体与有向关系，PostgreSQL 存储，不引入 Neo4j |
| 回答引用与原文定位 | 回答里的引用角标可跳到原文件位置并高亮；不同格式有 page/block/sheet/text 定位 | **统一引用系统**：题目、笔记、文档、图片、报告之间都能互相引用；利用现有 `QuestionSource` 的 quote + offset 机制扩展 |
| Wiki 版本历史 | 版本区分自动生成 / Agent / 人工编辑 / 回滚；支持比较、回滚，回滚也产生新版本 | **文档版本对比**：把已有历史版本从「编辑器里的列表」升级为时间线 + 前后 diff + 来源说明 |
| 图片与文件访问抽象 | 内部引用与外部访问分离，便于跨渠道复用 | 只借鉴「稳定引用」思想；**不引入 MinIO/S3/对象存储** |

### 2.2 明确不学的部分

以下能力对 OpenStudy 当前阶段收益低、成本高，且用户明确说不需要「其他服务器方面的东西」：

- 不引入 Neo4j、APOC、独立图数据库；
- 不引入 docreader/gRPC/Python 解析服务；
- 不引入 MinIO/COS/S3 等对象存储后端；
- 不引入多租户、组织、RBAC、审计平台；
- 不引入 MCP、技能沙箱、自动化任务；
- 不照搬 WeKnora 的 Neo4j/Wiki 部署链路；实体图谱用 PostgreSQL 表实现。

我们要的是 **交互范式和信息架构**，不是它的部署架构。

## 三、四个方向的取舍

### 方向 1：画廊 —— 建议作为 0.4.0 的 P0

**用户价值**：现在「图片墙」只是把当前资料夹里 `imageMap` 摊开，图片没有名字、没有描述、没有 OCR、不能按内容搜，用户只能靠眼睛翻。画廊要解决的是「我记得有一张图，但我不记得在哪份资料里」。

**产品形态**：

- 入口：我的资料 → 画廊（替换现有「图片墙」）。
- 范围：当前资料夹 / 全部资料；文档图片 / 独立图片 / 表格截图。
- 导航：路由导航直接进入全局最顶层顶栏，使用面包屑（我的资料 / 当前资料夹 / 当前视图）+ 工作台 tabs（资料夹 / 书架 / 画廊 / 知识图谱）；内容区不再重复一套头部。
- 卡片：瀑布流排布，保留图片原始比例形成自然高度梯度；卡片内显示缩略图 + 来源文档 + 图片类型 + 描述摘要 + 是否已描述。
- 搜索：图片文件名、图片描述、OCR 文本、来源文档名一起搜。
- 详情：大图、描述、OCR、来源文档、所在章节、被哪些题目/笔记引用。
- 批量操作：只在文档级或画廊顶部出现一次「为未描述图片添加描述」，不在每张图片卡上重复添加按钮。

**图片描述怎么接 LLM**：

- 不是只发一张图给模型；
- 输入包 = 图片 + 文档标题 + 所在章节标题 + 图片前后各一段文字 + 已有 OCR 文本（如果有）；
- 输出 JSON：`caption`、`ocrText`、`kind`（photo / diagram / table / formula / screenshot）、`keywords`、`confidence`；
- 文档上传时**默认不生成**，只标记「未描述」；
- 用户点一次批量按钮后才生成；单张图片在详情页可以单独补描述；
- 描述结果可作为图片资产索引，后续进入 RAG 搜索。

**不增加心智负担的设计**：

- 文档行不新增一排按钮；只在文档更多菜单 / 下拉中有一个「为图片添加描述」；
- 画廊顶部只有一个「补全未描述图片」动作；
- 同一份文档已描述完成时，动作显示「图片已描述」而不是再次请求；
- 聊天回答末尾只在检测到文档图片且尚未描述时追加一个按钮，不重复、不弹窗。

### 方向 2：知识地图 —— 建议作为 0.4.1 的 P1，不建议先做

WeKnora 的 Wiki 图谱很好，但它的基础是 **Wiki 页面**：文档先被 LLM 整理成 summary/entity/concept 页面，页面之间再通过 `InLinks/OutLinks` 形成图。直接照搬会出现两个问题：

1. **我们没有 Wiki 页面层**，强行画图只能画文档/章节节点，关系没有内容；
2. **没有引用数据**，图上的边只能靠“看起来相关”，无法解释为什么连在一起。

**建议的 OpenStudy 版本**：

- 节点不叫「实体」，叫「资料页」：
  - 文档摘要页；
  - 章节页（来自现有 `document_health` 的 sections / outline）；
  - 笔记页（用户已有笔记）；
  - 题目/图片只在详情里作为「关联内容」，不单独铺满图。
- 边来自可解释关系：
  - 文档层级（父子章节）；
  - 引用关系（笔记引文档、题目引原文、文档引图片）；
  - 同一来源文档的聚合；
  - 语义相似只做辅助，不单独作为强边。
- 分组按「来源文档 / 资料夹 / 主题」；
- 组上显示主题说明（LLM 根据组内页面标题 + 摘要生成一次，缓存）；
- 交互采用 WeKnora 的成熟模式：聚焦分组、分组菜单、返回全图/Esc、隐藏无关联页、搜索和页面类型筛选；
- 节点点击打开页面详情，详情里有「来源文档摘要页」链接，再跳原文。

**技术边界**：

- 不建 Neo4j；用现有关系表 + 邻接表即可；
- 不要求一次生成全部 Wiki；先做「章节页 + 文档摘要页」；
- 图布局在前端完成，避免新增服务。

### 方向 3：引用系统 —— 建议作为 0.4.0 的 P0，是知识地图的前置

这是四个方向里**技术含量最高、也最能支撑「可追溯」叙事**的一项。

**统一引用模型**：

```text
ContentReference
- id
- user_id
- source_type: document | document_chunk | document_image | note | question | prescription_task
- source_id
- source_sub_id: chunkId / imageSeq / questionId
- target_type: document | note | question | image
- target_id
- quote: 引用原文，最多 N 字
- start_offset / end_offset
- created_by / create_time
```

现有 `QuestionSource` 已经解决了「题目 → 文档 chunk + quote + offset」，0.4.x 应把它抽象成统一的 `ContentReference`，并保留旧表兼容迁移。

**前端体验**：

- 文档正文、笔记正文中出现引用标记（上标数字/小卡片），点击打开右侧来源面板；
- 来源面板显示：来源文档、章节、原文 quote、定位偏移、被引用次数；
- 点击「定位原文」进入 `DocumentAnatomyPanel`，滚动到对应 offset 并高亮；
- 笔记编辑器支持「插入引用」：选中文档/章节/图片/题目，插入后保存引用关系；
- 图片详情显示「被哪些题目/笔记引用」；
- 未来 `LearningPrescription` 的任务也能引用原文，形成「学习任务 → 原文 → 题目」的证据链。

**关键原则**：

- 引用不是超链接，必须有**来源 + 位置 + quote**；
- 先支持只读引用和定位，再做编辑器插入；
- 任何引用失败都要明确提示「来源不可用」，不能静默跳错。

### 方向 4：版本迭代 —— 建议作为 0.4.0 的 P1，是演示加分项

现有代码已经有 `RagDocument.version`、`MaterialOrganizeLog`、编辑器里的「历史版本」，但用户看不到“改了什么、为什么改、前后差多少”。

**0.4.x 版本面板**：

- 文档详情增加「版本」入口（不是新页面，复用现有抽屉/弹窗）；
- 时间线显示：版本号、时间、来源（上传 / AI 整理 / 手动编辑 / 回滚）、操作者、一句变更摘要；
- 选中两个版本可做左右对比：新增/删除/改写按颜色标出；
- 对比旁边显示健康报告变化（综合分、问题数、结构/覆盖等），让“AI 整理有效”变成可验证结果；
- 一键恢复，恢复后自动生成新版本，不覆盖旧版本；
- PPT 演示用「v1 → v2」真实界面讲，而不是口头说“支持版本”。

## 四、0.4.1 视觉化方案：资料星图

知识地图不是把节点丢给力导向算法，更不是画一张“看起来很智能”的实体图。0.4.1 采用**三层结构 + 固定视觉语法**，保证在真实资料量下仍然读得懂、演示得出来。

### 4.1 三层结构

1. **总览层（全图/当前资料夹）**
   - 只展示资料页、题组、图组、笔记；章节页默认收起。
   - 每个资料夹是一组，资料页使用该组的主色。资料量最多的组拿到主色蓝，避免默认资料夹变成沙金色。
   - 每份资料的题组、图组、有真实引用的笔记，围绕资料页形成一个小簇。

2. **聚焦层（点开一份资料）**
   - 该资料的章节页围绕资料页展开，其他页面降低透明度。
   - 章节页显示标题和字数；点击章节进入右侧详情，点「定位原文」打开资料刨析。
   - 右侧面板显示摘要、章节数、题目数、图片数、版本；不做无来源的“AI 评价”。

3. **详情层（右侧可读面板）**
   - 固定展示节点标题、摘要、章节正文摘录、来源资料、真实引用记录。
   - 资料节点提供「查看资料」「展开章节」；章节/笔记节点提供「定位原文」。
   - 所有动作都通向已有模块（资料刨析、资料体检、笔记/题库），不新建孤岛页面。

### 4.2 视觉语法

| 对象 | 形状 | 颜色/说明 |
|---|---|---|
| 资料页 | 圆形 | 按资料夹分组着色，大小只由真实正文字数决定 |
| 章节页 | 小圆点 | 聚焦时才出现，避免总览层变噪声 |
| 笔记 | 圆角矩形 | 只显示存在真实引用的笔记 |
| 题组 | 菱形 | 数字来自 `QuestionSource` 的真实计数 |
| 图组 | 方形 | 数字来自 `RagImageAsset` 的真实计数 |
| 引用边 | 紫色虚线 | 来源→目标可解释，面板能展开 quote/offset |
| 归属边 | 浅灰/浅金/浅青细线 | 文档→章节、文档→题组、文档→图组 |

背景使用浅色点阵纸张，不用深色科技大屏；颜色控制在雾蓝、青绿、陶土、淡紫、沙金五组，适合答辩投影和截图。

### 4.3 布局算法（前端完成，不新增服务）

- 按资料夹计算分组；组数 ≤ 4 时按 2×2 网格，更多时按 `ceil(sqrt(n))` 网格。
- 组内资料页用黄金角向日葵分布，避免同心圆挤在一条线上。
- 题组/图组/笔记围绕所属资料页做小轨道；没有归属的笔记靠近组中心。
- 聚焦时章节页按 128px 轨道展开；退出聚焦或按 Esc 即回收。
- 用 ECharts `scatter + lines` 而不是 `graph` 力导向：位置可控、文字可读、不会出现节点抱团或椭圆变形。
- 左侧分组列表、顶部搜索/隐藏孤立页、右侧详情共同组成“可读地图”，而不是只能旋转缩放的装饰图。

### 4.4 验收标准

- 首次打开：10 秒内能看出“有几个资料夹、每个资料夹有多少资料”；
- 点开资料：章节、题目、图片、笔记的关系能解释，且能跳回原文；
- 搜索一个词：命中的页面及其直接邻居保留，其他页面收起；
- 没有引用时不画假虚线，没有笔记时不造笔记节点；
- 1440 宽屏下三栏完整；窗口变窄时隐藏右栏但保留地图与分组；
- 截图中不出现空白大块、乱线、重叠标签。

### 暂不做

- 不做完整 Wiki 自动写作；
- 不做多租户/对象存储/MCP/沙箱；
- 不做为了“看起来智能”而生成的假统计数字。

## 六、数据与接口草案（只讨论思路，不绑定具体实现）

### 5.1 图片资产

建议新增 `rag_image_asset`：

```text
id, user_id, kb_id, doc_id nullable, image_key, source_type(document|chat|standalone),
file_path, file_name, kind(photo|diagram|table|formula|screenshot),
section_index, section_title, offset, surrounding_text,
caption, ocr_text, keywords, description_status(pending|processing|done|failed),
description_model, described_at, create_time
```

- 文档图片：`image_key = doc:{docId}:{seq}`；
- 聊天图片：`image_key = chat:{imageId}`；
- 现有 `MaterialAssetUsage.asset_key` 可以继续复用，补充图片描述不改变用途账本。

接口草案：

- `GET /rag/gallery?scope=current|all&source=doc|chat|standalone&q=...`
- `GET /rag/gallery/{assetKey}`
- `POST /rag/gallery/describe`（批量，按 docId 或 assetKeys）
- `GET /rag/gallery/describe/progress/{taskId}`
- `POST /rag/gallery/{assetKey}/describe`（单张补描述）

### 5.2 引用

- `GET /rag/references?targetType=note&targetId=...`
- `POST /rag/references`
- `DELETE /rag/references/{id}`
- `GET /rag/references/{id}/source`（返回来源定位信息）

### 5.3 知识页面/图

- `GET /rag/knowledge-pages?docId=...`
- `GET /rag/knowledge-map?scope=...`
- `GET /rag/knowledge-map/{pageId}`
- 边关系直接由 `ContentReference` + 文档层级生成，不额外存 Neo4j。

## 七、3 分钟演示脚本（0.4.1）

1. **0:00–0:30 画廊**
   - 打开「我的资料 → 画廊」；
   - 搜索「受力分析」或「第 3 章表格」；
   - 结果里同时出现文档图片和聊天独立图片，卡片标出来源文档。

2. **0:30–1:10 图片理解**
   - 打开一张图片详情，看到描述、OCR、来源章节；
   - 点击「为这份文档补齐未描述图片」；
   - 只出现一个批量动作，进度显示“已完成/总数”。

3. **1:10–1:50 引用**
   - 在笔记里插入对这张图片/这段原文的引用；
   - 阅读页出现引用标记，点击跳回原文并高亮；
   - 面板显示来源、章节、原文 quote。

4. **1:50–2:30 知识地图**
   - 打开资料知识地图：按文档/章节分组；
   - 点击「概率论」组聚焦，隐藏无关联页；
   - 点章节页看摘要，再跳回来源文档摘要页。

5. **2:30–3:00 版本**
   - 打开文档版本：v1 → v2，查看 diff；
   - 显示来源「AI 整理」、变更数量和复检健康变化；
   - 一键恢复，形成完整可信闭环。

这个演示的核心不是“我们也有画廊/图谱”，而是：
> **每张图都有来源，每条引用都有位置，每个节点都能回到原文，每个版本都能解释和回滚。**

## 八、为什么这比“资料装配”更有创新性

| 维度 | 资料装配 | 0.4.x 资料知识网络 |
|---|---|---|
| 用户目标 | 生成一份文件 | 找到、引用、理解、复用资料 |
| 系统角色 | 一次性生成器 | 持续积累的知识基础设施 |
| 数据沉淀 | 生成文本，难复用 | 图片描述、引用关系、页面关系持续沉淀 |
| 可解释性 | 依赖 LLM 解释 | 来源 + 位置 + quote + 版本 |
| 演示效果 | 看一段生成文本 | 搜图 → 引用 → 跳原文 → 看关系图 → 看版本 |
| 技术深度 | Prompt 工程 | 资产索引、引用模型、图关系、版本 diff、检索 |
| 与现有模块关系 | 相对独立 | 连接资料、题目、笔记、学习处方、学情 |

## 九、风险与取舍

1. **不要一次做四个方向的全量版**
   - 先 0.4.0 的「画廊 + 引用 + 版本」，再做 0.4.1 的知识地图。
2. **图片描述成本和延迟**
   - 默认不自动跑；按文档/图片批量触发；失败可重试，不阻塞上传。
3. **引用标记的编辑器改造**
   - 先做只读展示和来源定位，再做 Tiptap 插入引用；不要一开始重写编辑器。
4. **知识地图容易变成“漂亮但没用”**
   - 没有引用关系就不做图；先有 0.4.0 的引用数据。
5. **不要伪造数据**
   - 图片描述、OCR、版本 diff、健康变化都必须来自实际运行结果。

## 十、建议的下一步

- 先确认 0.4.0 的「画廊 + 引用」两条线；
- 我可以先做一版**画廊交互原型**（数据先用现有 `image_map` + 独立图片，描述接口后接）；
- 同时梳理 `QuestionSource` → `ContentReference` 的迁移方案；
- 知识地图在引用数据稳定后再开工，避免做成空图。
